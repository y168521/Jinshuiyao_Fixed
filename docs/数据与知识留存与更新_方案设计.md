# 数据与知识留存与更新 · 方案设计

> 适用对象：金水谣「长期记忆 / 知识库 / 规则 / 自动化 / 教训经验 / 文档 / 技能 / 智能体」八类资产（分级见 `金水谣_知识资产总纲.md`）。
> 设计日期：2026-10-02　状态：**待实现**（核心模块见 `core/infra/knowledge_store.py`）
> 本文档只做**方案选型与规则定义**，不含代码。

---

## 结论先行

| 问题 | 方案 | 一句话理由 |
|---|---|---|
| 用什么存 | **JSONL 事件日志（WAL，主）+ JSON 快照（物化）+ 可选 SQLite（索引加速）** | JSONL 崩溃安全且天然产生版本链；快照保持人可读、能被现役 `safe_json` 生态消费 |
| 为什么不全用 JSON | 6MB 级 JSON 每次改一个字就要全量重写，写放大严重且**丢历史** | 现役 `knowledge/vector_index.json` 已 6MB |
| 为什么不全用 SQLite | 引入依赖 + 与现役 JSON 生态割裂 + 非人可读，违反「四副本 mtime 比对」等现役铁律 | 降级为**可选加速层** |
| 怎么做到更新即生效 | 索引**增量更新** + 检索缓存按 **(mtime, size)** 双键失效 | 现役 `_cached_asset` 只按 mtime，同秒写入会漏（见 §3.5） |
| 历史怎么留 | 每次变更 append 一个新版本（`rev+1`，`supersedes` 指旧），**旧版本永不覆写** | 追溯/回滚天然可用 |
| 冲突怎么办 | **乐观锁**：写时校验 `base_rev`，不匹配即拒绝并报冲突 | 静默覆盖才是真敌人（MEMORY 闸门铁律） |

## 一、现状盘点：能复用什么，缺口在哪

> 本节全部为**实测**结论（读代码 + 读文件），不是估计。

| 能力 | 现役模块（真源） | 现役接口 | 是否复用 | 缺口 |
|---|---|---|---|---|
| 原子写 + 校验和 | `utils/safe_json.py` | `safe_write_json(path,data,embed_checksum,backup)` | ✅ 复用 | 只有 3 个滚动备份，**无时间戳版本链**，无法按时间点回滚 |
| 损坏恢复 | `utils/safe_json.py` | `safe_load_json(...)` 自动回退备份 | ✅ 复用 | 只回退到"最近一个能用的"，不知道退到了哪版 |
| 锁 | `utils/locks.py` | `json_lock/corr_lock/preds_lock/log_rotate_lock` | ⚠️ 部分 | 全是 `threading.Lock()`（**非重入**），与「重入 RLock」铁律冲突 → 嵌套获取会死锁 |
| 三元组原子写 | `knowledge/triple_store.py` | `load/save_triple_store` + `_TRIPLE_STORE_LOCK` | ✅ 复用模式 | 无版本历史、无软删除、无冲突检测 |
| 检索缓存失效 | `core/infra/knowledge_gateway.py` | `_cached_asset(key, loader, path)` | ✅ 复用 | **只按 mtime**，同秒连续写入 mtime 可能相同 → 脏读 |
| 规则新鲜度 | `utils/lottery_prize.py` | `rules_staleness()`（180 天） | ✅ 复用思路 | 仅覆盖奖级规则，未推广到全部知识资产 |
| 知识分级 | `金水谣_知识资产总纲.md` | L0~L4 + draft/verified/proven | ✅ 直接落地 | 尚无存储层承载 |

**一句话**：地基（原子写、锁、缓存失效、新鲜度判据）都在，缺的是**统一的版本化存储层**。本方案只补这一层。

## 二、持久化设计

### 2.1 存储介质选型

| 候选 | 优点 | 缺点 | 结论 |
|---|---|---|---|
| 纯 JSON 文件 | 人可读、零依赖、现役生态成熟 | 全量重写、写放大、无版本链 | **降级为快照层** |
| **JSONL append-only** | 崩溃安全、O(1) 追加、天然版本链、可 tail 增量 | 需压实、随机读要索引 | ✅ **主存储（WAL）** |
| SQLite | 事务、索引、SQL、并发好 | 新增依赖、非人可读、与四副本 mtime 机制割裂 | ⚠️ **可选加速索引** |
| 向量库 | 语义检索 | 重依赖、成本高 | ❌ 否（现役 BM25 够用） |

**决策：JSONL(WAL) + JSON(快照)，SQLite 可选。** 零强制新增依赖，纯标准库可跑。

### 2.2 结构化格式

```
金水谣数据/knowledge_store/
├── records.jsonl          # 主存储：一行一条事件（append-only，永不覆写）
├── index.json             # 物化索引：ns:key -> {latest_id, rev, offset, length}
├── snapshot/              # 快照：按 ns 导出的 JSON，供人类/现役工具消费
│   └── <ns>.json
└── archive/               # compact 归档 + 回滚点（只增不删）
    └── records_<ts>.jsonl
```

**records.jsonl 单行格式**（一行一个事件，四种事件类型）：

```json
{"ev":"put","id":"k7f3a1","ns":"经验","key":"JS-20260925-10","rev":1,"ts":"2026-10-02T06:30:00",
 "payload":{...},"meta":{"schema":1,"author":"WorkBuddy","source":"经验收集箱.md",
 "tags":["协作","最佳实践"],"tier":"L0","maturity":"draft","status":"active",
 "expires_at":null,"supersedes":null,"base_rev":0,"checksum":"sha256:...","acl":"internal"}}
```

| 事件 | 含义 | payload |
|---|---|---|
| `put` | 新增或一个**新版本** | 完整内容 |
| `patch` | 增量更新（只带变更字段） | 变更字段子集 |
| `deprecate` | 标记过期/失效（**不删内容**） | `{"reason": "...", "superseded_by": "id"}` |
| `delete` | 软删除墓碑 | `{"reason": "..."}` |

### 2.3 元数据设计（`meta` 字段）

| 字段 | 类型 | 用途 | 必填 |
|---|---|---|---|
| `schema` | int | 结构版本，兼容旧数据 | ✅ |
| `author` | str | 来源（WorkBuddy / qoder / 人工 / 脚本） | ✅ |
| `source` | str | 溯源到哪个文件 | ✅ |
| `tags` | list | 九域标签（沿用经验箱体系） | ✅ |
| `tier` | str | L0~L4 层级（总纲） | ✅ |
| `maturity` | str | draft / verified / proven | ✅ |
| `status` | str | active / deprecated / deleted | ✅ |
| `expires_at` | str\|null | 过期时间（ISO） | — |
| `supersedes` | str\|null | 上一版本 id（版本链） | — |
| `base_rev` | int | 乐观锁基线 | ✅ |
| `checksum` | str | payload 的 sha256（一致性校验） | ✅ |
| `acl` | str | public / internal / secret | ✅ |

### 2.4 索引设计

| 索引 | 结构 | 用途 |
|---|---|---|
| 主键 | `id -> {offset, length}` | O(1) 定位到 JSONL 行 |
| 业务键 | `ns:key -> {latest_id, rev}` | 按业务键取最新版本 |
| 状态 | `status -> [id...]` | 快速筛 active/deprecated |
| 倒排（检索） | 复用现役 BM25 `_tokenize` | 全文检索，内存构建 |

**索引本身也是文件**（`index.json`），用 `safe_write_json` 原子写；进程内维护增量副本，避免每次全量重建。

## 三、CRUD 与增量更新

### 3.1 写入路径（Create / Update）

```
put(ns, key, payload, meta)
  ├─ 加 RLock（重入，防嵌套死锁）
  ├─ 读当前 latest.rev → base_rev
  ├─ 若调用方传了 expect_rev 且 != base_rev → 抛 ConflictError（不静默覆盖）
  ├─ 计算 checksum、supersedes=latest.id、rev=base_rev+1
  ├─ append 一行到 records.jsonl（写完整行 + flush + fsync）
  ├─ 增量更新内存索引（不重建）
  └─ 标记索引脏 → 异步落盘 index.json
```

### 3.2 读路径（Read）

- `get(ns, key)` → 走 `ns:key` 索引拿 `latest_id` → 按 `offset` seek 到 JSONL 行 → 反序列化
- `get_version(id)` → 直接定位
- `history(ns, key)` → 沿 `supersedes` 链回溯，返回全部版本

### 3.3 更新（Update）—— **追加新版本，不覆写**

| 方式 | 适用 | 说明 |
|---|---|---|
| `put` 全量 | 内容小（< 64KB） | 直接写新版本，旧版本保留 |
| `patch` 增量 | 内容大（如 6MB 索引） | 只存变更字段，**物化时合并**，避免写放大 |

### 3.4 删除（Delete）—— **软删除**

- append 一条 `delete` 墓碑，`status=deleted`，**内容不物理删除**
- 物理删除只在 `compact` 时发生，且**必须先落 `archive/`**
- 理由：MEMORY 铁律「副本治理＝保内容+保链接+断写入，不直接删」

### 3.5 更新后检索/查询即时生效

| 环节 | 机制 | 说明 |
|---|---|---|
| 索引 | **增量更新**（append 后直接改内存索引） | 不重建全量 |
| 检索缓存 | 失效键 = **(mtime, size)** | **修正现役缺陷**：`_cached_asset` 只按 mtime，Windows 下同秒连续写入 mtime 相同 → 脏读。加 size 后同秒也能区分 |
| 跨进程 | 依赖 mtime/size 变化触发重载 | 无需 IPC；多进程最终一致 |
| 网关接入 | 新增 `knowledge_store` 为第五源 | 与现役 cards/triples/experiences/project_docs 并列 |

## 四、过期 / 失效 / 冲突的识别与清理

### 4.1 过期（时间驱动）

- 每条可带 `expires_at`；扫描任务按 `KB_DEFAULT_TTL_DAYS` 兜底
- 到期 → append `deprecate` 事件，**内容保留**，只是 `status=deprecated`
- 与现役 `utils/lottery_prize.py::rules_staleness`（180 天）同思路，推广到全资产

### 4.2 失效（事实驱动）

| 情形 | 识别方式 |
|---|---|
| 溯源文件已删除/移动 | 检查 `meta.source` 路径是否存在 |
| 与代码实际行为冲突 | 一致性检查比对代码常量（**以代码为准，回修文档**） |
| 被更新结论取代 | 人工/自动置 `superseded_by` |

### 4.3 冲突（并发驱动）—— 乐观锁

- 写入须带 `expect_rev`；不匹配 → `ConflictError`，返回当前最新 rev 与新版本差异
- **绝不静默覆盖**（MEMORY：「守卫有两种失败模式：报错和静默，静默才是真敌人」）
- 自动合并策略：仅对 `patch` 且字段不交集时允许自动合并，否则报冲突

### 4.4 清理与 compact

- `compact()` 重写 JSONL：丢弃 `delete` 墓碑与被 `supersedes` 覆盖的**中间版本**（保留首尾）
- **硬约束（骤降守卫）**：若重写后条数少于原条数的 50%，**拒绝写入并告警**
  （依据 MEMORY：JS-20260925-06 `data_maintenance` 把 predictions.json 从 3258 条硬截到 200 条的事故）
- compact 前**必须先落 `archive/`**，留回滚点

### 4.5 版本追溯与回滚

| 操作 | 实现 |
|---|---|
| 看历史 | `history(ns,key)` → 沿 `supersedes` 链 |
| 回滚到某版 | `rollback(ns,key,rev)` → 以该版内容 append 一个**新版本**（不删历史） |
| 时间点恢复 | 按 `ts` 过滤事件重放到该时刻 |

> 回滚也是"新增版本"，**历史只增不减** —— 这样回滚本身也可被回滚。

## 五、延伸问题

### 5.1 一致性校验

| 校验项 | 方法 | 失败处理 |
|---|---|---|
| 单行可解析 | `json.loads` 逐行 | 截断尾部半行（可恢复） |
| checksum 匹配 | 重算 payload sha256 | 标记 `corrupt`，**不丢弃** |
| 索引↔日志一致 | `offset/length` 抽样校验 | 不一致 → 重建索引 |
| 外键存在 | `supersedes` 指向的 id 存在 | 告警（不阻断） |
| 与代码常量一致 | 比对标准真源 §三 | **以代码为准并回修文档** |

### 5.2 失败重试与容错

- 写入重试：`RETRY_MAX` 次，指数退避（`RETRY_BASE_SLEEP` 秒）
- **失败必须抛错，禁止 `except: pass`**（MEMORY：静默失败会让闸门变哑巴）
- JSONL 只 append，崩溃最多丢最后一行（未 fsync 的部分），**不会损坏已有数据**
- 临时文件用 `tmp + os.replace` 原子替换（复用 `safe_json` 模式）

### 5.3 备份与恢复

| 层级 | 机制 | 保留 |
|---|---|---|
| 事件级 | JSONL 全历史（本身就是备份） | 永久（直到 compact） |
| 文件级 | `utils/safe_json.auto_backup` 滚动备份 | 3 个（现役） |
| 归档级 | `archive/records_<ts>.jsonl` | compact 前必落 |
| 恢复 | 按 id / rev / 时间点重放 | — |

### 5.4 权限与隐私合规

| 项 | 规则 |
|---|---|
| 分级 | `acl` = public / internal / secret（元数据必填） |
| secret | **禁止**进入知识库正文与索引；密钥一律走 `~/.jinshuiyao-secrets/`（现役铁律） |
| 出索引 | `secret` 级记录不参与倒排与网关召回 |
| 商业化 | 项目有商业化意向（2026-08-11）→ **接数据源前先过授权评估**，外部抓取内容须标来源、不冒充官方 |

### 5.5 扩展与维护成本

| 维度 | 评估 |
|---|---|
| 依赖 | **零新增强制依赖**（纯标准库）；SQLite 为可选 |
| 写放大 | JSONL O(1) 追加；大对象用 `patch` 增量 → 避免 6MB 全量重写 |
| 膨胀控制 | `compact` + 骤降守卫；可按 ns 分片降低单文件大小 |
| 迁移成本 | 快照层仍是 JSON，现役工具（`safe_json`、网关）无需改动即可消费 |
| 人力 | 新增一致性检查项接入 `check_consistency.py`（第 ⑬ 项） |

## 六、关键流程与边界情况

| # | 边界情况 | 处理 |
|---|---|---|
| 1 | 同秒连续写入 | 缓存失效键加 `size`，防 mtime 相同导致脏读 |
| 2 | 写入中途崩溃 | JSONL 尾部半行 → 下次加载截断到最后一个 `\n` |
| 3 | 并发写同一 key | 乐观锁 `expect_rev`，冲突报错不覆盖 |
| 4 | 同一 RLock 嵌套获取 | 必须用 `threading.RLock()`（现役 `locks.py` 是普通 Lock，需新增 RLock 或改造） |
| 5 | compact 误删 | 骤降守卫（<50% 拒绝写入）+ 先落 archive |
| 6 | 索引与日志不一致 | 校验失败自动重建（重建是安全的，因为日志是权威） |
| 7 | 记录过期但仍被引用 | 只标 `deprecated`，**不删**；引用方显式处理 |
| 8 | secret 泄漏进日志 | 写入前按 acl 过滤；secret 级拒绝入库 |
| 9 | 跨进程看不到最新 | 依赖 mtime/size；提供 `refresh()` 强制重载 |
| 10 | 回滚后又要回滚 | 回滚 = 追加新版本，历史只增不减 |
