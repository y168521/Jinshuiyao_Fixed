## 0. 问题背景与立项依据

当前数据几类共存、边界模糊，且已发生真实事故：

- **运行时数据**（`金水谣数据/`）：json 日志、决策卡 `log/ai_decisions.md`、彩票健康报告等，被 server 与多个 AI 会话频繁读写。
- **用户知识库/经验箱**（`knowledge/`，含 `用户知识库/`）。
- **源码/配置/真源**：git 跟踪的 `.py`/`.json`/`.md`，以及 `启动提示词.txt`、`AGENTS.md`。
- **演示 vs 真实**：`matches` 场景已做物理隔离（`jinshuiyao/data/matches_real.csv` 真实、`matches_supplemented.csv` 演示），但仅为单点实践，未形成全局机制。

**近期真实事故（驱动项④）**：多 AI 会话并发写同一仓库（四文档 + 决策卡）导致 **撞号 + 悬空提交 + 文件互相覆盖**，③开发期与四件套留痕期各发生一次。证明"共享数据无写租约"是高危项。

**风险登记册呼应**：`金水谣数据/risk_register.json` 中 R-002（`mitigation_status = 待落地(项④)`）的缓解方案明确为"本地备份三层（活/副本/保险，属项④）+ git 版本化 + 依赖①门禁去盲区发现能力"。本 PRD 是 R-002 的既定缓解手段落地依据，④落地后该状态应更新为"已落地"。

## 1. 产品目标（Product Goals）

1. **故障隔离（Isolation）**：按"易变性 / 重要性 / 可重建性"将运行数据分到三层，使单层的损坏、误写、丢失、勒索或并发写冲突 **不跨层扩散**，保证可恢复、可审计。
2. **写串行化（Serialization）**：对共享高频写文件引入写前租约、写后释放（复用 `scripts/session_coordinator.py` 的 `acquire/release/heartbeat`），**杜绝多 AI 会话并发互删/覆盖**（直击撞号+悬空提交事故），并与后续⑤会话租约形成基础衔接。
3. **可恢复与可审计（Recoverability & Auditability）**：周期性副本快照 + 版本化保险真源，使任意关键改动可倒查溯源（呼应 `模型/工作留痕总索引.md`），并在活层误改/丢失时回退到最近恢复点。

> 正交性：目标1管"空间隔离"，目标2管"写时序"，目标3管"时间回溯"，三者互不重叠。

## 2. 用户故事（User Stories）

1. **As 主理人（诺亚）**，我希望运行数据按易变性分层存放，以便单层的损坏/误写/丢失不扩散到其他层，保证系统始终可恢复。
2. **As 多 AI 会话协作者**，我希望写共享文件前先获取写租约，以便不会并发互删/覆盖（避免撞号 + 悬空提交事故重演）。
3. **As 运维/主理人**，我希望有自动周期副本快照与一键恢复脚本，以便在活层误改、勒索或丢失时回退到最近恢复点（RPO 可知）。
4. **As 审计者**，我希望保险层真源受版本控制且活层无法误改，以便任何关键改动可倒查溯源（呼应工作留痕总索引）。
5. **As 数据生产者**，我希望真实数据与演示数据物理隔离且全局生效，以便演示/补充数据不会污染真实真源（推广 matches 单点实践为全局铁律）。

## 3. 三层模型定义与边界（核心结论）

论证：从"活(live) / 副本(replica) / 保险(insurance)"三档切入，按 **易变性↓、重要性↑、可重建性↓** 递进。每层用"物理目录 + 读写权限 + 丢失后果"三维界定，保证单层故障不跨层。

### 3.1 活层（Live / 工作副本）
- **放什么**：运行时高频易变、被 server 与多 AI 会话频繁读写的文件。例：`金水谣数据/brain_state.json`、`predictions.json`、`correlation_matrix.json`、`log/ai_decisions.md`（决策卡）、`log/经验收集箱.md`、`free_model_status.json`、`lot_data/`、`users/`、`review/`、`fund_data/`、`stock/` 缓存等。
- **不放什么**：源码真源（`.py`）、受版本化的重要成果、真实数据真源。
- **谁可读写**：server、AI 会话、脚本均可读写；但写共享文件须先 `acquire` 租约。
- **丢失后果**：**可接受**短暂丢失/回退——可重建或从副本层恢复；损坏范围应被隔离在本层，不波及其他层。

### 3.2 副本层（Replica / 周期快照）
- **放什么**：活层关键文件的周期快照（沿用并系统化现有 `*.json.bak.0~2` 三代轮转思路）。位置 `金水谣数据/backups/`（当前仅有 `gui/` 子目录，需扩展为统一副本层）。
- **不放什么**：实时运行态文件、源码真源。
- **谁可读写**：**仅备份脚本可写**；任何人可读（fail-safe：副本生成失败只告警，不阻断主流程）。
- **丢失后果**：**可接受**——退化为只能从保险层恢复（粒度更粗），但数据仍不丢。

### 3.3 保险层（Insurance / 版本化真源）
- **放什么**：
  - (a) git 跟踪的真源/配置/文档：`.py` 源码、`config/*.json`、`启动提示词.txt`、`AGENTS.md`、`docs/*` 架构稿/PRD；
  - (b) 需版本化的重要运行时真源：`金水谣数据/risk_register.json`（R-002 owner=备份机制项④，已约定 json 受①门禁守护 + git 版本化）、`jinshuiyao/data/matches_real.csv`（真实数据真源）、知识库/经验箱重要成果；
  - (c) 受控脚本写入、活层只读的"运行时重要成果归档"：新建 `金水谣数据/insurance/`（决策卡/经验箱归档、risk_register 快照等），与活层写路径完全脱钩。
- **不放什么**：实时运行态、派生快照（副本层已覆盖）。
- **谁可读写**：人类/受控流程（git commit、门禁、受控备份脚本）可写；**活层运行时代码只能读，不能写**（防误改）。
- **丢失后果**：**几乎不可接受**——这是最终防线；靠 git 远程/坚果云 + 版本历史兜底。

### 3.4 三层对照表

| 维度 | 活层 Live | 副本层 Replica | 保险层 Insurance |
|------|-----------|----------------|------------------|
| 易变性 | 高（分钟级） | 中（快照时点） | 低（受控变更） |
| 物理位置 | `金水谣数据/`（运行时子目录） | `金水谣数据/backups/` | git 仓库真源 + `金水谣数据/insurance/` |
| 写权限 | server/AI/脚本（共享文件需租约） | 仅备份脚本 | 人类/受控流程；活层只读 |
| 是否 git 跟踪 | 否（`.gitignore` 排除） | 否（派生快照，排除） | 是（真源/文档/risk_register） |
| 丢失后果 | 可接受（可重建/可回退） | 可接受（退化到保险层） | 不可接受（最终防线） |
| 失败姿态 | fail-safe 告警 | fail-safe 告警 | 受控写、强校验 |

## 4. 隔离机制（Isolation Mechanisms）

1. **物理目录隔离**：活层（`金水谣数据/`运行时）↔ 副本层（`金水谣数据/backups/`）↔ 保险层（git 真源 + `金水谣数据/insurance/`）三目录边界清晰。保险层核心（源码/配置/文档）本就与运行时物理分离（仓库根 vs `金水谣数据` 子目录）。新增 `金水谣数据/insurance/` 存放活层无法误改的版本化快照，与活层写路径完全脱钩。
2. **写锁/租约（Write Lease）**：对共享高频写文件（决策卡、经验箱、brain_state、predictions、知识库）引入写前 `acquire(intent)`、写后 `release()`，复用 `scripts/session_coordinator.py`（`acquire/release/heartbeat`，30min 心跳自愈）——与⑤会话租约共用底层，避免重复建设；非共享文件无需租约以免性能损耗。
3. **备份周期与保留**：副本层按重要度分频（决策卡/经验箱/预测：每 N 分钟；大文件：每日），滚动保留（建议 24×每小时 + 7×每日 + 4×每周），沿用并系统化现有 `.bak.0~2` 三代轮转。
4. **保险层防误改**：活层运行时无保险层写权限；保险层真源仅经 git/受控脚本写入；建立"**活层可写路径白名单**"，任何非白名单路径写操作触发 `[G]` 告警（与①门禁"默认只告警不阻断"一致）。

## 5. 与现有约定衔接（Conventions & Continuity）

- **git 只跟踪真源/保险层**：运行时 json 不入库，沿用 `.gitignore` 约定（已排除 `金水谣数据/*` 运行时、`*.json.bak.*` 等）。副本层/保险快照（派生数据）同样排除；insurance 目录中的"受版本化真源"（源码/文档/risk_register.json）保持入库。
- **演示/真实数据物理隔离 → 全局规则**：`matches_real.csv`(真实) vs `matches_supplemented.csv`(演示) 单点实践 **推广为全局铁律**——所有"真实赛果/真实用户数据"与"演示/补充/脱敏数据"必须物理分文件/分目录，命名含 `_real` / `_demo` / `_supplemented` 后缀，演示数据不污染真实真源（呼应③数据铁律）。
- **fail-safe 姿态**：默认告警不阻断、不硬失败。沿用①门禁"默认只告警不阻断 / verify 硬失败"；④所有隔离/备份/租约异常一律降级为 `[G]` 告警（写告警日志），不抛异常阻断主流程。
- **风险登记册联动**：④落地后 R-002 `mitigation_status` 由 `待落地(项④)` 更新为 `已落地`；R-003 的"写租约"基础由④提供（写串行化），"全局快照"归⑤/⑥。
- **门禁联动**：副本/保险完整性自检与① `jinshuiyao_data_guard`（STRONG 12 目录/21 文件守护）联动——金水谣数据强校验项缺失→告警（R-002 early_signal）。

## 7. 待确认问题（Open Questions）

4. **④与⑤/⑥边界**：④负责"写串行化 + 三层物理隔离 + 副本快照"；⑤负责"会话级租约统一编排"；⑥负责"全局快照一致性"。是否把"写租约"完全交给⑤、④只做目录与副本？建议④内置基础写锁（复用 `session_coordinator`）即可，⑤做统一编排，避免重复建设。请架构师在系统设计中明确接口归属。
