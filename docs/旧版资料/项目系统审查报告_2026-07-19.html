③ 数据流断裂（核心问题）

🔴 [P0] 双知识库存储互不连通

项目存在两套并行、互不同步的知识库：

库存储形态当前卡片数被谁写入被谁读取
库A · MiroFishDBknowledge/mirofish_db.json90/api/knowledge/add、/api/knowledge/extract-archive工作台「知识库」视图（/api/knowledge/list）、全局搜索
库B · 用户知识库knowledge/用户知识库/*.md + INDEX.json7/api/video/ingest（视频归档）、video_to_kb.py无前端视图读取

后果：你之前通过「视频文案提取」归档的抖音视频卡片，写入了库B（markdown），但工作台的「知识库」标签页只读库A（MiroFishDB）。这 7 张视频知识卡在前端完全不可见，形成「提取成功却看不到」的逻辑断裂——正是你反复遇到的"功能像没生效"的根因之一。

改进：二选一——(a) 视频归档同时写入 MiroFishDB（推荐，统一索引）；或 (b) 工作台知识库视图合并读取两套库。并删除冗余的 /api/knowledge/extract-archive（与 /api/video/ingest 功能重叠却写不同库）。

🟡 [P2] 预测记录自动写入无管控

/api/chat 每次对话都自动调用 record_prediction() 写入 predictions/predictions.json，无去重、无上限。长期运行会持续膨胀单文件 JSON，且无并发锁（见⑤）。

④ 安全隐患

🔴 [P1] 明文凭证落入云同步目录（高危泄露）

  • Jinshuiyao_Fixed/config/douyin_cookie.txt —— 内含真实抖音登录态（sessionid、sid_guard、passport_* 等完整 cookie）。
  • Jinshuiyao_Fixed/deepseek_key.txt —— DeepSeek API Key 明文。

这两个文件都位于坚果云同步根目录之内，且项目没有 .gitignore / .nutstoreignore 排除它们 → 会被同步到云端及其他设备。更矛盾的是 video_extractor.py 第 78 行注释写着「⚠️ 切勿提交到仓库/云同步」，但文件本身恰恰放在同步目录里。

改进：① 将密钥移出同步目录（如 C:/Users/Administrator/.jinshuiyao-secrets/）；② 或在 .nutstoreignore 中排除 config/douyin_cookie.txt、deepseek_key.txt、*.log；③ 密钥文件权限设为仅当前用户可读。

🔴 [P1] SSRF + 知识库污染（守卫遗漏）

/api/knowledge/extract-archive 缺少 _is_local() 守卫（对照 /api/video/ingest 第 1195 行有守卫）。它接受任意 URL 并由服务器代发 HTTP 请求、写入 MiroFishDB。

局域网任意用户可借此：① 让服务器访问内网/云元数据（http://169.254.169.254/）实施 SSRF；② 向知识库注入任意垃圾卡片污染数据。

改进：补 _is_local() 守卫 + 对传入 URL 做 scheme/host 白名单校验（仅允许 http/https 且非内网地址）。

🟡 [P2] open_local_file 路径穿越（纵深防御缺口）

/open 端点调用 open_local_file(rel_path)，内部仅做 os.path.join(BASE_DIR, rel_path)，未校验解析结果仍位于 BASE_DIR 之内。若传入 ..\..\windows\... 可逃逸项目目录（仅能"打开/查看"非执行，且已 localhost 限制，但属纵深防御缺口）。

改进：解析后用 os.path.commonpath([BASE_DIR, full]) == BASE_DIR 校验，拒绝越界路径。

🟢 已做对的防护（应予保留）

  • 执行类接口（/open、/api/run-tests、/api/video/ingest、/api/memory 写、/sync-api/*）均有 _is_local() 守卫 ✓
  • 静态服务 _serve_static 拒绝含 .. 的路径段（防目录穿越）✓
  • do_GET/do_POST 外层 try/except，异常返回 500 JSON 不挂起 ✓
  • 视频提取 cookie 仅用户手动提供，不偷浏览器 ✓
  • /health 健康检查已加（且 AI 检测已改为仅看密钥文件，避免超时）✓

⑤ 边界情况与性能瓶颈

🟡 [P2] 单线程服务器 = 慢请求阻塞全局

服务器使用默认 http.server（单线程）。任何慢请求都会阻塞后续所有请求：

  • /api/chat 调 DeepSeek（网络往返，可能数秒~数十秒）
  • /api/video/ingest 联网抓取视频页（已实测数秒）
  • /api/run-tests 最长 60 秒

改进：改用 ThreadingHTTPServer（一行改动），让请求并行处理；对外部调用加整体超时。

🟡 [P2] JSON 存储无并发锁

mirofish_db.json、predictions/predictions.json 均为「读全文件→改内存→写全文件」，无文件锁。当前单线程无碍，但一旦线程化或多进程即可能损坏（已存在 .bak.0/1/2 旋转文件，暗示历史上出过问题）。且 _load 在 JSON 损坏时直接回退空库 → 静默丢数据。

改进：统一用 tempfile + os.replace 原子写（已有 utils.safe_json，确保所有写路径都走它）；损坏时优先从 .bak 恢复而非回退空库。

🟡 [P2] 写接口缺请求体大小上限

以下写接口无 Content-Length 上限，可投放大请求撑爆内存/JSON：/api/knowledge/add、/api/knowledge/extract-archive、/api/memory(POST)、/api/route。对照 /api/chat(10000)、/api/ask(10000)、/api/video/ingest(20000) 已有上限，标准不统一。

改进：统一在读取 body 前加 if cl > 1_000_000: 400。

🔵 [P3] 其他边界/性能细节

  • log() 每次调用都 open(LOG_FILE,'a') 再写 → 高并发 I/O 放大，建议改用 logging 模块 + Handler。
  • 硬编码 Python 候选路径含 D:\python38 与 TRAE 私有路径 → 跨机脆弱，建议仅用 shutil.which/本机探测。
  • 记忆增删改用整行精确匹配（ln.strip()==target），条目含前后空格或重复文本会误匹配，建议改用稳定 id。
  • 工作台知识库视图初始用硬编码 sampleKnowledge(8 条) 兜底，接口异常时展示示例而非"加载失败"提示。
  • 无 requirements.txt/pyproject.toml，依赖（如 requests）未锁定，复现困难。
  • CORS Access-Control-Allow-Origin: * 全开，配合未守卫接口可被跨站页面调用，建议按接口收紧。
  • 根目录存在 jinshuiyao_bat_test.log 及被坚果云锁定的临时文件，建议加 .nutstoreignore 排除日志/临时文件并定期清理。

⑦ 改进方案与落地路线

优先级 P0/P1（建议 1~2 天内完成）

  1. 统一知识库存储：让 /api/video/ingest 在写入 markdown 库的同时，也写一条摘要卡到 MiroFishDB（或反之），并删除冗余的 /api/knowledge/extract-archive。前端「知识库」视图即可看到全部归档。
  2. 密钥移出同步目录：新增 .nutstoreignore 排除 config/douyin_cookie.txt、deepseek_key.txt、*.log、.uploads/；并将两文件物理移动到同步目录外（如 ~/.jinshuiyao-secrets/），修改 video_extractor 与 ai_service 的读取路径。
  3. 补 localhost 守卫 + URL 白名单：/api/knowledge/extract-archive 加 _is_local()，并对传入 URL 校验 scheme=http/https 且 host 非内网。

优先级 P2（建议 1 周内完成）

  1. 服务器线程化：main() 改用 ThreadingHTTPServer，外部调用统一加超时。
  2. 原子写 + 损坏恢复：所有 JSON 写路径统一走 utils.safe_json，加载失败时优先从 .bak 恢复。
  3. 统一请求体上限：所有写接口加 cl > 1_000_000 → 400。
  4. 路径穿越校验：open_local_file 加 commonpath 校验。
  5. 预测记录限流：record_prediction 仅记录结构性结论，加单文件条数上限（如 5000）。

优先级 P3（持续打磨）

  1. 用 logging 模块替换 log() 的每次 open。
  2. Python 路径探测改为纯 shutil.which/本机探测，删硬编码盘符。
  3. 记忆系统改用稳定 id 增删改，替代整行匹配。
  4. 补 requirements.txt，锁定 requests 等依赖。
  5. 收紧 CORS，按接口设置 Access-Control-Allow-Origin。
  6. 建立「模块调用地图」文档，标注各子系统活跃度，避免误改未串联代码。
