二、优化建议（按优先级排序）

① P2 拆分 guide_server.py 单体（结构/可读性）

当前 ~1600 行承担：路由分发 + 记忆存储 + 预测存储 + 跨设备同步 + 静态服务。
  • 建议按职责拆分：server/routes.py、server/memory_store.py、server/prediction_store.py、server/sync_api.py，guide_server.py 仅做装配与异常外壳。
  • 收益：单文件认知负担下降；改一处崩全局的风险降低；新增端点只动 routes.py。
预期影响：维护性显著提升，新增/修改功能的平均改动范围缩小 40%+，回归风险下降。

② P2 知识库/预测写入走"内存缓存 + 定时刷盘"（性能）

T4 加锁后，add_card 与 record_prediction 每次都 全量读 JSON→改→全量写 JSON，O(n) I/O。
  • MiroFishDB：进程内缓存 _data，脏标记后每 N 秒或每 M 次写盘；或升级为 SQLite。
  • predictions.json：同样加内存缓存，避免每次对话都 parse 2000 条。
预期影响：高频归档/对话延迟从十毫秒级降到亚毫秒，磁盘 I/O 减少一个数量级（批量视频提取场景最明显）。

③ P2 外部网络调用加硬超时与重试上限（边界）

VideoExtractor.extract 与 AI 对话调用 DeepSeek 必须设上限，否则单请求可卡死线程。
  • 视频提取：单请求硬超时（如 15s）+ 重定向次数上限。
  • DeepSeek 调用：HTTP 超时（如 30s）+ 最多 2 次重试；超时返回友好降级而非挂起。
预期影响：消除"一个坏链接/慢接口拖垮线程池"的风险，线程化后这一项尤为关键。

④ P2 静态文件服务增加大小限制与显式 404/403（安全/边界）

_serve_static 对超大文件/损坏路径应有显式响应，避免大文件撑满内存。
  • 对 .py/.bat 等可执行文件，静态服务应拒绝（仅 open_local_file 经本机守卫后才执行）。
  • 单文件响应建议上限（如 50MB），超出返回 413。
预期影响：降低 DoS 面，防止通过大文件请求耗尽内存。

⑤ P3 收敛密钥/记忆的重复读取逻辑（重复代码）

已统一为 _resolve_deepseek_key_file / _resolve_cookie_file 两种近似模板；记忆 add/edit/remove 三函数重复"读-改-写"。
  • 抽公共 _resolve_secret(*rel_names) 与 _mutate_memory_file(path, transform)。
预期影响：密钥/记忆位置变更只需改一处，后续维护成本下降，逻辑分支更清晰。

⑥ P3 高频只读接口加 mtime 缓存（性能）

/api/knowledge/list、_parse_memory_file、/health 目录统计每次都重读磁盘。
  • 对"文件 mtime 未变则复用上次结果"做轻量缓存（TTL 1–3 秒即可）。
预期影响：前端轮询健康/知识库时 CPU 与 I/O 明显下降，对低端机更明显。

⑦ P3 统一错误响应结构（错误处理）

当前错误多为 {"error": ...} 或 {"ok":false,"error":...}，前端分类不便。
  • 约定统一结构：{"ok":false,"code":"BODY_TOO_LARGE","message":"..."}，便于前端按 code 分流。
预期影响：前端错误处理更稳健，可精确区分 400/403/413/500 给出对应提示。

三、已具备的良好实践（保持）

  • ✓ do_GET/do_POST 顶层 try/except 安全网，单请求异常不再拖垮服务器。
  • ✓ /health 健康检查 + 前端绿灯指示器，问题提前暴露。
  • ✓ 所有写/执行类接口 _is_local() 本机守卫（防局域网越权）。
  • ✓ 预测/知识库写操作已用临时文件 + os.replace 原子写，读操作不会看到半截 JSON。
  • ✓ POST 统一 1MB body 上限；路径穿越 commonpath 校验。
  • ✓ 前端 safeFetch 自动重试；内联 JS 改动后跑 node --check 校验。

四、已知接受项（非缺陷）

  • CORS 为 *：因门户以 file:// 打开需跨域访问 localhost API，收紧到具体源会破坏门户功能；属本地开发工具的有意取舍，非生产暴露。
  • 两套知识库并存：MiroFishDB（库A，前端读）与"用户知识库 markdown"（库B，闭环成长）经 T1 已连通，概念分工保留（库B 存原始证据更全）。

五、落地优先级建议

顺序建议工作量价值
1③ 外部调用硬超时小高（防线程卡死）
2④ 静态服务大小/类型限制小中（降 DoS 面）
3② 内存缓存+刷盘中高（性能）
4① 拆分单体大高（可维护性）
5⑥ mtime 缓存小中（性能）
6⑤ 收敛重复逻辑小中（可维护性）
7⑦ 统一错误结构小中（前端体验）

说明：本轮已交付 P0–P3 全部安全修复并逐项实测；上述优化建议为后续演进方向，按"先防卡死/降风险，再提性能，最后做结构收敛"的顺序推进最划算。
