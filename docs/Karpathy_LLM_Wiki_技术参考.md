# Karpathy LLM Wiki 方法论 · 技术参考

> 整理来源：Andrej Karpathy 2026-04 发布的 gist《LLM Wiki》原文，及 luoli523 / xdlkc / cncsmonster / NemoClaw / xieyan0811 等中文深度解读。
> 重要定位：这是一套**个人知识库的构建方法论**，不是讲 LLM 内部原理（Transformer / 训练 / 推理）的教科书。它回答的是「知识如何长期组织、沉淀、复利」，而不是「模型怎么工作」。

---

## 一、核心概念与基础理论

### 1. 知识编译 vs 知识检索（与 RAG 的根本差异）
- 传统 RAG（检索增强生成）：每次提问时，从原始文档切块 → 检索相关片段 → 模型**临时**拼出答案。能答，但「每次都要重新发现知识」，没有沉淀、没有复利。
- LLM Wiki（知识编译）：新资料**一进来**就由 LLM 先「编译」成结构化 Wiki；之后基于这个 Wiki 问答。Karpathy 原话：*“The knowledge is compiled once and then kept current, not re-derived on every query.”*（知识先编译一次并持续更新，而不是每次查询都重新推导。）
- 一句话区别：**RAG 是查资料；LLM Wiki 是养一个会长大的知识库。**

### 2. 知识复利（persistent & compounding artifact）
- Wiki 是「持久 + 复利增长」的知识产物：
  - **持久(persistent)**：落在文件系统的 Markdown，不是临时聊天上下文，会话结束仍在。
  - **复利(compounding)**：新资料让 Wiki 变厚；新问答产生的比较/判断/连接，可写回 Wiki；后一次使用站在前一次积累上。
- 复利 ≠ 线性堆积。线性只是越堆越多；复利是旧认知被重新关联、比较、修正，产生更好的综合，再写回成为新基础。

### 3. 关键比喻
- *“Obsidian 是 IDE；LLM 是程序员；Wiki 是代码库。”*
- 含义：这不是笔记 App，而是人和模型共同维护的「知识代码库」。

### 4. 它真正解决的痛点
- 知识库失败的主因不是「读不懂」，而是「维护成本随规模暴涨」：更新交叉引用、修订摘要、标冲突、维持几十页一致性——人最不愿做也最耗意志力。
- LLM 擅长做高频、低创造性、跨文件的一致性维护，正好补上这一层。
- 本质：把知识管理从「存档系统」（目标是别丢）推进成「编译系统」（目标是形成结构）。

## 二、体系架构设计（三层）

| 层 | 角色 | 职责 | 谁控制 |
|---|---|---|---|
| **raw/** 证据层 | 素材库 | 文章、论文 PDF、图片、数据集，只增不改（immutable） | 人（负责收集与筛选） |
| **The Wiki** 知识层 | 成品区 | LLM 生成的 Markdown：摘要/实体/概念/综述页 + 索引 | LLM 拥有(maintenance) |
| **The Schema** 配置层 | 规则层 | CLAUDE.md / AGENTS.md，定义目录结构、模板、流程、质检标准 | 人与 LLM 共同演化 |

### Wiki 内的页面类型
- **摘要页**：每份原始资料的关键要点提炼。
- **实体页**：人物、组织、技术的专属页。
- **概念页**：抽象概念的解释与关联。
- **综述页**：跨多个来源的主题综合分析。
- **索引文件(index.md)**：全局目录与导航；Query 时 LLM 先读它再进相关页。中等规模(~100 来源、数百页)下，甚至可暂时不用 embedding RAG。
- **日志(log.md)**：append-only 时间线，记录 ingest/query/lint 发生了什么（可用 `grep "^## [" log.md` 查）。

> 单向编译关系：raw → wiki。raw 是证据，wiki 是解释与综合。

## 三、工作流方法（三大流程）

### 1. Ingest（摄入）
往 raw/ 放新资料 → LLM 读原文 → 与你讨论关键要点 → 写摘要页 → 更新相关概念/实体页 → 更新 index.md → 记 log.md。
- 一次摄入可能触及 **10–15 个 Wiki 页面**——这正是 LLM 维护的核心价值（人不可能每加一份资料就手动更新十几个页面）。

### 2. Query（查询与写回）
LLM 先读 index.md → 定位相关页 → 综合作答并附引用来源。
- **关键机制**：质量够好的答案，作为新页面/更新**写回 Wiki**。
- 你每次探索不是一次性消耗，而是持续增值的投资。没有写回，Wiki 会退化成「整理过的 RAG」。

### 3. Lint（健康检查）
定期让 LLM 检查 Wiki 健康：
- 页面间是否矛盾、新来源是否推翻旧 claim；
- 是否有孤立页(orphan)、是否缺交叉引用；
- 重要概念被提到却无独立页、是否存在 data gaps（值得继续搜资料）。
- Lint 是「防腐机制」：防止幻觉累积、结构臃肿、维护债务。

### 复利的闭环
`摄入资料 → Wiki 变厚 → 查询产生新综合 → 写回 → Wiki 再变厚`。人和 LLM 的分工：**LLM 负责维护劳动；人负责资料选择、方向判断、可信度决策**（Human owns trust & promotion）。

## 四、外部关系、背景与风险治理

### 1. 与 RAG 不是替代，而是补「中间层」
- Karpathy 批评的是「切块→嵌入→查询时临时拼答案」的默认范式，不是所有检索。
- 对于中等规模、高价值、需长期累积理解的语料，光有 retrieval 不够，还需要 **synthesis layer（综合/结构层）**。

### 2. 与微软 GraphRAG 呼应
- 微软《From Local to Global》(2024)：传统 RAG 难答「整个语料的主题是什么」这类全局问题（本质是 query-focused summarization）。
- GraphRAG 把原文编译成**实体图谱+社区摘要**；LLM Wiki 把原文编译成**人可读的 Markdown Wiki**。两者都在原始材料与最终问答间加一层「提前整理过的知识表示」。
- 区别：GraphRAG 适合大规模、程序化、图结构显著的企业语料；LLM Wiki 适合个人研究、中型项目、强调可读可编辑。

### 3. 为什么 2026 年才可行（context engineering 背景）
- 模型已擅长「文件系统级工作」（读写、跨页更新、增量维护）——带工具调用的 agent 适合这种事。
- Simon Willison(2025)、Anthropic(2025) 的 context engineering 共识：下一步推理前把「刚刚好的信息」放进上下文，比写漂亮 prompt 更重要。LLM Wiki 本质是 **agentic memory / 上下文外部化**。
- 长上下文变大但「上下文腐烂」仍在：有组织的 5 万 token 常比无组织的 50 万 token 更有价值。

### 4. 四大风险（越强大越需治理）
1. **错误被编译进去**：聊天里的错随会话消失，Wiki 里的错会变长期资产反复被调用——幻觉复利危害远大于一次性答错。
2. **过度确定性 / 合成性失真**：模型综合多篇时，易把尚不确定、彼此冲突、证据等级不同的内容，写成表面连贯但不够谨慎的结论。
3. **可维护 ≠ 可审计**：Markdown 比向量库透明，但无来源引用/更新时间/冲突标记/事实等级，仍会沦为一堆看似可信的二手改写。
4. **团队扩展治理陡增**：语料来自 Slack/会议/客户通话时，涉及权限、版本、责任归属、事实冲突——不是 prompt 能解决的。

### 5. 治理原则（降低幻觉复利）
- 保留 raw 证据层、不篡改原始来源；
- 重要 claim 尽量带来源或证据链接；
- 区分**事实 / 解释 / 推论 / 待验证**；
- query 写回不能无脑进高置信层；
- Lint 不只查孤立页/坏链，也要查无来源 claim、过时判断、被当事实的推论。

## 五、对你（金水谣 AI 知识库）可直接借鉴的点

对照你现有的 `Jinshuiyao_Fixed/knowledge/用户知识库/`：
- **加 raw 层**：现在的卡片是直接写的「成品」，没有不可改的原始来源。可加 `raw/` 放你参考的网页/文档，卡片从 raw 编译而来，便于溯源。
- **加 schema 层**：现在缺 `CLAUDE.md/AGENTS.md` 规定结构。补一份「如何写卡、如何分类、何时写回」的规则，跨会话一致性才有保障。
- **加 Lint 流程**：现在只有写入+索引，没有定期健康检查。可加一个「查矛盾/孤立/数据空洞」的定期脚本。
- **区分事实与推论**：现在卡片把问答答案直接存为「内容」。应标注哪些是高置信事实、哪些是模型推论/待验证，避免幻觉复利。
- **Query 写回**：现在的智能助手问答已能写回（`archive_knowledge_qa`），方向对了——但要配合上面几点才能复利而不"复错"。

> 一句话：**你的知识库现在是「单层存档」，Karpathy 给的是「三层编译 + 三大流程 + 治理」的完整范式。** 不必全搬，先补 raw 层 + schema 层 + Lint，就能从"别丢"升级到"长结构"。
