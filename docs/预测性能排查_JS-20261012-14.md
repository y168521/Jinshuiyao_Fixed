# 预测性能排查报告（JS-20261012-14）

> 排查时间：2026-10-12 08:32 ｜ 现象：用户反馈「现在的预测怎么有点慢」
> **结论：97% 的时间花在一次「对出号并非必需」的 AI 简报调用上，且该调用经常失败、失败后不缓存，导致每次重复付费。**

## 一、结论（结论先行）

| 项 | 结论 |
|---|---|
| 慢不慢？ | **确实慢**：实测 5 个彩种共 **336.4 秒（约 5.6 分钟）** |
| 时间花在哪？ | **97.6% 在 AI 调用**（`ensure_daily_brief` → `_ai_json` → 免费模型 HTTP），大乐透 124.7s 中 121.7s 是 AI |
| 出号本身慢吗？ | **不慢**。缓存命中时快乐8 仅 **2.9 秒** |
| AI 简报必需吗？ | **非必需**。简报失败（返回 None）时 `generate` 仍 `success=True`，正常出号 |
| 为什么每次都重付？ | AI 失败后**不写缓存** ⇒ 大乐透/排列三的简报缓存仍停在 **2026-09-02**（40 天前），每次点都重付 ~123s |

## 三、根因链

1. `PredictionService.generate()` 对每个彩种调 `ensure_daily_brief(lot, arr)` 取「AI 每日简报」。
2. 简报按 **彩种 + 天** 缓存（`金水谣数据/brain/ai_brief_<lot>.json`），故 5 个彩种 = 最多 5 次 AI 调用。
3. `call_ai_failover()` 默认 `timeout=120`，遍历免费模型池逐个尝试 —— 实测 **3 个模型各约 40s**。
4. 免费模型返回内容无法解析成 JSON ⇒ `_ai_json` 返回 None ⇒ `_build_brief` 返回 None ⇒ **不写缓存**。
5. 下次再点 ⇒ 又付一遍 120s。大乐透/排列三的缓存因此停在 2026-09-02。

**关键矛盾**：这 5.6 分钟花在一次「失败了也不影响出号」的调用上——`success` 始终为 True，号码照常生成。

## 四、优化建议（按性价比排序）

| # | 建议 | 预期收益 | 风险 |
|---|---|---|---|
| 1 | **简报改为「先出号、简报后台补」或加「跳过 AI 简报」开关** | 336s → **约 15s（~20×）** | 低：简报非出号必需，已有 None 兜底 |
| 2 | **降低简报超时**：`call_ai_failover` 的 `timeout` 由 120s 降到 15~20s | 最坏 360s → 约 75~100s | 低：简报是辅助建议，宁可快速降级 |
| 3 | **加负面缓存**：AI 失败当天也记一笔，不再重复重试 | 当天第二次起免付费 | 低；需注意别把「首次真故障」永久固化 |
| 4 | **并发化**：5 个彩种的简报并行取 | 336s → 约 124s（取最慢者） | 中：需处理并发写缓存与预算控制 |

**建议优先做 1 + 2**，二者组合可把体感从 5.6 分钟降到十几秒，且不动出号逻辑。

## 五、诚实边界（未验证）

- 未验证「跳过 AI 简报」会否影响出号**质量**（hot/kill 号码可能参与出号）。已验证**不影响能否出号**（success=True）。
- 免费模型失败的具体原因（超时 / 返回非 JSON / 熔断）未逐个取证，仅从「耗时 40s ×3 + 缓存未更新」推断为失败。
- 实测在 WorkBuddy 沙箱内完成，与 GUI 实际运行环境（后台服务）可能有差异，但耗时量级应一致。
