# 未知问题处理标准方案（JS-20261012-17）

> 适用场景：遇到项目记忆 / 知识库 / 文档**未覆盖**的新问题，或缺少依据、不确定如何处理时。
> 原则：**先全网检索多方方案与社区经验 → 对比可行性与风险 → 选最优解**；检索不到或信息不完整时，结合项目已有约定自行补全并**显式标注为推断**。
> 引用外部结论**必须注明来源，不得凭空编造**。

## 一、问题背景（为什么必须立这条标准）

本仓两次因"凭既有思路直接落地"而引入本可避免的缺陷：

1. **线程超时**（JS-20261012-16）：我按既有经验用 `threading.Thread + join(timeout)` 给 AI 调用加超时，自认为"已经限时"。检索后才知道——**线程超时只是停止等待，杀不死已在跑的工作**。若未标注，后来者会误以为超时即取消。
2. **负面缓存锁死一天**（同上）：我按直觉把失败"按天"缓存。检索后才知道这是**经典反模式**：瞬时故障被锁死后，用户修好根因错误依旧不消失。

共同点：**两者的代码都能跑通、单测都能过，但语义是错的**——属于"静默失败"，靠自测发现不了。故必须强制先检索。

## 二、判断依据（什么情况必须检索）

满足任一即触发检索（**不要凭记忆直接动手**）：

| 触发条件 | 例子 |
|---|---|
| 涉及**并发 / 超时 / 缓存 / 重试 / 熔断**等有成熟社区共识的领域 | 本例线程超时、负面缓存 |
| 涉及**外部权威数值**（费率、返奖率、法规条款） | 财政部返奖率、PIPL 条款 |
| 要**改变默认值或既有行为** | 把 AI 简报默认关掉 |
| 涉及**合规 / 商业化**边界 | 能否宣称预测能力 |
| 记忆里只有"结论"没有"出处" | 记忆写了返奖率但没写来源 |
| 我要下的结论会被**写进文档对外呈现** | 概率概念对照、能力边界 |

**反过来**，纯项目内部的机械操作（留痕三件套、GITSYNC、门禁提交）不必检索，按既有铁律执行即可。

## 三、解决步骤（5 步）

1. **界定问题，先区分"能不能做"与"该不该做"**
   - 例：简报"能不能跳过"（会不会出不了号）vs"该不该跳过"（它有没有用）。先确认前者，再谈后者。
2. **全网检索多方方案**（≥2 个独立来源，优先权威一手源）
   - 数值类：官方公告 / 政府网站 / 标准原文（如财政部公告、PIPL 原文）
   - 工程类：成熟社区的共识与反模式列表（如 Python 官方并发文档取向、缓存模式综述）
   - **交叉验证**：两个来源说法一致才采信；冲突时以更权威者为准并在文档注明分歧。
3. **对比可行性与风险，选最优解**
   - 列出候选方案与各自风险，明确"最优解是什么、为什么当前只能用次优解"。
   - 例：超时最优解是**库层超时**（`socket.settimeout` / `requests timeout`），因 `chat()` 不暴露参数才退而用线程兜底——**必须把"这是次优解"写进注释**。
4. **落地实现 + 把检索到的注意事项固化进代码与单测**
   - 坑写进 docstring（后来者看得到）；防线写成**断言**（机器守得住）。
5. **沉淀结论**：写入本文档的"实战案例"，并同步进 `MEMORY.md` 与留痕三件套（交接中心 / 总索引 / 经验箱 / 本轮事项）。

## 四、注意事项（坑，每条都有出处）

1. **线程超时 ≠ 杀死工作**：`future.result(timeout=)` / `join(timeout)` 只停止**等待**，worker 仍被占用；真正停止需库层超时或进程 + `terminate()`。来源：Python 并发实践综述（pythonpool.com《Python Function Timeout》）、async-concurrency《Timing Out Blocking Calls in Threads》"Do Not Pretend Threads Kill Work"。
2. **负面缓存 TTL 必须远短于正面缓存**，且要能自愈：正面常 5~30 分钟，负面 30~90 秒（错误状态 5~30 秒 + 指数退避）。把失败"锁死一天"是反模式——用户修好根因后错误依旧。来源：Software Patterns Lexicon《Negative Caching》、codemia《Negative Caching Explained》、Wikipedia《Negative cache》（明确指出某些情况下属 anti-pattern）。
3. **改默认值会让旧测试"假绿"**：新默认值下，旧用例测到的可能是"被开关挡掉"而非真实逻辑。改完必须回头检查相关旧用例，必要时显式开启开关以保住覆盖。
4. **单测要断言"有没有被调用"，不要只看返回值**：返回值 `None` 在"被开关挡掉"和"AI 失败"两种情况完全一样，只看返回值分不出对错。
5. **引用必须注明来源**：无法检索到依据时，明确标注"本项目推断，未获外部证实"，不得写成既定事实。

## 五、验证方式（每条都要可执行）

| 环节 | 验证方式 |
|---|---|
| 问题定位 | 用 profiler / 计时实测，不靠猜；用"命中 vs 未命中"对照跑同一函数切开瓶颈 |
| 方案选择 | ≥2 个独立来源交叉验证；冲突时记录分歧与取舍理由 |
| 代码实现 | **单测先红后绿**：改前必须看到失败（且失败原因要能复现原缺陷），改后转绿 |
| 不回退 | 跑相关回归（本例 47 项），含旧用例适配检查 |
| 真实效果 | **端到端**跑真实入口对比前后指标（本例 336.42s → 9.60s，提速 35.1×，且出号/期号不变） |
| 结论沉淀 | 写入本文档 + `MEMORY.md` + 留痕三件套，注明来源 |
