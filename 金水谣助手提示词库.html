代码优化三维框架优化/重构
目标：给 AI 一个明确的优化方向后，逼它按统一四维框架分析再动手，避免"直接改"漏维度、结论发散。四维＝方案探索 / 策略整合 / 参考调研 / 正反推导（正向思维+逆向思维交叉验证）。适用于任何代码优化 / 重构任务。
【请先在这里写明明确的优化方向，例如：优化 auto_knowledge.py 的三元组抽取性能】 在进行代码优化时，当给定明确的优化方向后，请从以下四个维度进行全面分析： 一、方案探索——提出多种可行的优化方案，逐一对比各方案在性能、可维护性、复杂度等方面的优劣； 二、策略整合——综合各方案的优点，取长补短，形成最优的整合策略并说明决策依据； 三、参考调研——查找类似问题的业界最佳实践和社区解决方案作为佐证； 四、正反推导——在方案落地前用两种对立思维交叉验证，避免盲区： · 正向思维：从目标与设计原则出发，正向推导「系统应该具备哪些能力」，核对现有方案是否覆盖全部目标路径，避免遗漏关键能力； · 逆向思维：从失败模式与最坏情况出发，反推「哪些漏洞必须堵死」，核对现有方案是否能抵御已知故障，避免存在未设防的崩溃点； · 交叉比对：正向推导的「必备能力」与逆向推导的「必堵漏洞」取交集＝必做项；两者差异＝需进一步验证的假设。 在此基础上，制定详细的、可分步执行的优化推进计划，明确每一步的具体目标、操作内容和预期效果。最后，给出优化完成后的后期维护与演进规划，包括持续监控、迭代方向和风险预案。整个分析过程需逻辑清晰、条理分明，确保结论具有可落地性。
正反推导运用指南（四维框架第四维怎么用）方法论
目标：把「正反推导」从一句口号变成可照做的步骤。用于任何优化 / 重构 / 架构决策 / 风险研判，在方案选定后做交叉验证，避免盲区。
【请在这里写明要推导的对象，例如：彩票抓取 S6 可观测性是否必须】 正反推导四步法： 第1步 列目标/原则（正向起点）：把对象的「应满足的设计目标」写成清单，例如高可用、数据准确、低运维、可观测。 第2步 正向推导（目标→能力）：对每条目标，问「系统现在具备哪些能力来满足它？」列出能力清单，标注已覆盖✅/缺口⏳。易犯的错：高估已覆盖。 第3步 逆向推导（故障→漏洞）：穷举真实故障模式（如 CWL404、乐彩连败、DNS败、全源挂、状态丢失、重复回归、源悄悄挂、历史污染），对每条问「当前方案能否抵御？」标注已堵✅/漏⏳。易犯的错：故障模式列不全就留盲区。 第4步 交叉比对：正向「必备能力」∩ 逆向「必堵漏洞」＝必做项（交集优先做）；两者差异＝待验证假设（不阻塞主线，单列跟踪）。 常见坑：①正向乐观、逆向悲观都偏；②交叉时只做交集会漏掉「仅一方独有」的高价值项（如逆向独有的历史债须专项）；③优先级用逆向「不做的后果」反推，避免把痛点根因排后面。 范例：S6 可观测性——正向看像锦上添花(可观测❌)，逆向看是故障定位刚需(源悄悄挂无人知→用户报500/404)，交叉判定＝必做且与 S5 并行。

目标：当用户报前端某功能"点了没反应/没效果"，或要求排查前端所有功能是否有同类隐藏 bug 时，系统化定位根因（缺失方法→500 / 重入锁→死锁挂起），避免凭感觉乱改。适用：金水谣 Web 总台/前端功能失效排查。沉淀自 JS-20260725-07。
【请在这里写明要排查的前端功能，例如：一键审查点了没反应】 请对金水谣 Web 前端做全端点审计并定位"没反应"类 bug，按以下步骤： 一、确认 server 在跑：用 py -3.14 启动，端口 18888，GET /health 须 200；改码后必须重启加载新码。 二、写审计脚本（Python urllib）批量打活 server 全部 GET/POST 端点（约 42 个），抓 HTTP 码 + 响应片段前若干字节，输出成表。 三、异常分类定位： · 500 + AttributeError 'GuideHandler' object has no attribute 'X' → handler 调了 GuideHandler 未实现的方法。修复：在 server/router.py 的 GuideHandler 补该方法（如 _read_body() 配对 _send_json() 统一读 POST body）。 · 请求挂起（curl 连接建立但无响应、server 日志无新错，区别于 500）→ 典型死锁。根因常是 threading.Lock() 不可重入：同线程持锁内再抢同锁。修复：改 threading.RLock()（跨线程仍串行）。案例：knowledge/vector_index.py 的 _BUILD_LOCK，get_vector_index() 持锁内调 build_index_from_kb() 再抢同锁。 · 404 → 先确认前端真实 method（GET/POST），排查是否测试脚本 method 误用，勿直接判 bug（control-center.html 注释"与后端路由一致"）。 四、改完必须 py -3.14 重启 server 实测端点恢复（如 vector/search 应 ~0.5s 返回语义结果，review/trigger 应返回完整报告）。 五、清理审计副作用：冒烟可能往 金水谣数据/log/ai_decisions.md 误写假决策卡，须用 Python 精确删对应行，验证尾部干净。 铁律提醒：① 本机 Edit 与 Bash 在 bypass 沙箱下不共享 FS，临时脚本用完 rm -f；② git 对 CJK 路径的 -C 参数会误报 No such file，改用 cd <路径> && git ...；③ 收工必 git commit（仅提交源码/文档+留痕，运行时生成文件不提交）。
彩票/预测类"有效"主张的证伪·三数检验法方法论/审查
目标：当用户或外部模型报告宣称某彩票/预测策略"已验证有效/命中率高/累计盈利"时，用统一的三数检验法+双证据链把主张钉死或坐实，杜绝被幸存者偏差、正样本无分母、事后归因、版本号军备竞赛忽悠。沉淀自 JS-20260727-01~05。
【请在这里贴要审查的主张/报告，例如：某模型自称冷号补位命中87.5%】 请对该彩票/预测主张做证伪审查，不许照单全收，按以下步骤： 一、三数检验法（三面夹击，过不了任一关即证伪）： ① 去极值净值：从总盈亏里去掉最大单注中奖，看是否仍为正——盈利常来自一注运气，去掉即净亏。 ② 样本外命中率 vs 随机基准：walk-forward 只用 history[:i] 生成、检验第 i 期真实开奖；对每个预测生成"同规格随机注单"走同一判定逻辑（不用合成分布），求 gain=引擎命中率−随机命中率。gain≈0 即无预测力。 ③ 理论期望对照：总投入×(−50%) 是负期望值定论，长期必向其收敛；"没跑够长"的盈利是时间不够而非有效。 二、统计陷阱识别：小样本(n<30)必算威尔逊置信区间(n=8 时区间可达47%–99.7%，点估计无意义)；正样本(只报中奖)无分母=幸存者偏差；"组三后必开组六"类=先验概率废话(组六本占72%)，须减去先验看条件增量；min_hit=1(任中1码即命中)口径会把随机蹭奖伪装成有效。 三、双证据链：内部实测(金水谣诚实回测 gain 列)+外部权威交叉验证(学术论文/官方辟谣/神经网络实验)，避免信息闭塞自证。 四、结论定向：彩票是 i.i.d. 独立随机事件，历史对未来零信息量，无预测力是定论。唯一合法"战胜彩票"路径是结构性+EV(曼德尔买全组合/roll-down)非预测。可吸收的只有风控(预算封顶/熔断/砍大盘彩)+诚实(随机基准/非中奖概率声明)，选号规则全丢。 铁律提醒：结论必须内部+外部双证据；对用户保持理性娱乐提示、不保证结果。
