## 🔴 P0 — 必须立即修（证据确凿，已亲核）

### P0-1 静态文件服务可泄露密钥（安全）
- **位置**：`server/router.py` 的 `_serve_static`（仅拦截 `..` 穿越，**不限文件类型/后缀**）
- **问题**：从 `ROOT_DIR` 直接吐任意文件。`Jinshuiyao_Fixed/deepseek_key.txt` 真实存在且在可达范围内 → 任何能访问 18888 的客户端 `GET` 即可下载 DeepSeek API Key（同理 `.json` 状态、cookie/token 文件）。
- **建议**：
  1. 白名单限制可服务后缀：`.html/.css/.js/.png/.svg/.ico/.json(仅公开配置)`。
  2. 拒绝一切 `.txt/.py/.key/.env` 及含 `key`/`token`/`cookie`/`secret` 的文件名。
  3. 敏感文件移出 `ROOT_DIR` 之上（已存 `~/.tianshuiyao-secrets/`，但 deepseek_key.txt 仍在项目内，需删除并改读密钥目录）。
- **优先级**：最高。一行白名单即可根治。

### P0-2 回测命中判定失真（预测可信度）
- **位置**：`backtesting/engine.py` ≈ 行 140：`match_count = len(set(actual) & set(pred))`，配 `min_hit = 1`
- **问题**：用**集合交集**判定命中 → ①忽略位置/顺序 ②对重复号去重 ③"3 个预测号里任意 1 个出现在开奖号中"就算命中。这正是「回测 95%/100% vs 你感觉预测变差」的根因——回测分数虚高，不反映真实预测能力。
- **建议**：
  1. 按玩法定义真实命中：如排列三/3D 需**位置+数值全中**（直选）或**组选**匹配，而非集合交集。
  2. 命中级联：`直选 > 组选 > 未中`，分别计分，去掉 `min_hit=1` 的宽松判定。
  3. 回测与真实预测 `prediction_service` 共用**同一套命中判定函数**，避免两套口径。
- **优先级**：高。不改则所有回测数字无参考价值。

### P0-3 开奖数据 `time` 字段缺失（数据完整性 P1，✅ 已回填于 JS-20260723-36）
- **位置**：`fetchers/fetcher.py:234`（`item.get("date","")`）与 `fetchers/fetcher.py:308`（`"time": ""` **硬编码**）
- **问题**：
  - 双色球/大乐透 走 500.com HTML 解析分支（行 308）**压根不抓日期列**，直接写空。
  - 七星彩 等 CWL 分支（行 234）源数据无 `date` 字段 → 空。
  - **实际影响（勘误）**：双色球/大乐透/七星彩 `time` 全空。**但 S6 新鲜度门禁（`server/handlers/lottery.py:68`）按文件 mtime 计算，并不读 `time` 字段**，故 time 空**不破坏 S6**（原清单"连累 S6"表述已更正）。time 字段真实用途仅在 `models/lottery_data.py:135`（按 period 查开奖日期做展示/上下文）与 `core/auto_knowledge.py:1046`（知识卡文本）→ 属**数据完整性**问题，非破坏性 bug。
- **修复（JS-20260723-36，已完成）**：
  1. 前向修复：`fetchers/fetcher.py` 新增 `_norm_draw_date(s)`（去星期后缀，归一化 `YYYY-MM-DD`），接入 CWL/通用分支/3 个 500 解析器共 5 处 → 未来抓取自动带日期。
  2. 存量回填：`回填_time字段.py` 拉 500.com 历史页建期号→日期映射，回填 2522 条空 time + 归一化 668 条星期后缀 → **7 彩种 time 字段 100% 干净**（`YYYY-MM-DD`，0 空 0 非标）。
- **优先级**：数据完整性 P1（原误判为 P0）。已闭环，无需再修。

## 🟠 P1 — 应尽快修（功能/可信度隐患）

### P1-1 真实预测层与回测口径不一致（独立专项）
- **位置**：`prediction_service.py`（或 services 下预测模块）+ `predictions.json`
- **问题**：回测 95%/100% 而用户主观"预测变差"。两者可能用不同判定/不同数据源；回测是历史重放，真实预测是实时生成，需对齐口径并实测真实命中。
- **建议**：立项专项——①统一命中函数（复用 P0-2 修复后的）；②对 `predictions.json` 历史预测做真实命中复盘；③输出"真实命中率"指标替换回测虚高值。

### P1-2 回测样本过小、易过拟合
- **位置**：`backtest_results/backtest_v2_20260713_*.json`（仅 ~20 期）
- **问题**：20 期样本下 95%/100% 不具统计意义，且回测窗口可能未严格避免未来数据泄漏。
- **建议**：扩容到 100+ 期、按彩种分段、加入"滚动窗口"回测；报告需附置信区间。

### P1-3 并发「读-改-写」仍有漏锁风险
- **位置**：`core/auto_knowledge.py`、`core/kb_engine.py` 及 scheduler 共享状态处
- **问题**：已知锁（RLock / `_TRIPLE_STORE_LOCK` / `_expbox_extract_lock`）已覆盖主要路径，但需复查新增路由/调度任务是否有新的共享资源未加锁；网络调用是否误留锁内。
- **建议**：对 `ai_decisions` 监听、scheduler 新任务做一遍锁审计；坚持"锁内 reload 最新库→append→释放，网络调用留锁外"。

### P1-4 `/lottery-sources-health` 新鲜度门禁对空 time 彩种误报
- **位置**：`server/handlers/lottery.py` + `jinshuiyao-guide/lottery-sources-health.html`
- **问题**：依赖 `time` 算新鲜度；P0-3 修复前，3 彩种恒为 STALE，面板无意义。
- **建议**：P0-3 修复后复测；空 `time` 时显示"未知/待回填"而非假 STALE。
