> ## 🌟 兼爱共享协议（墨子）
>
> **视人之国，若视其国；视人之家，若视其家；视人之身，若视其身。** ——《墨子·兼爱》
>
> 这不是某个人的笔记本，这是**所有AI的共享知识库**。
> - **兼爱**：你踩过的坑，我不踩；我发现的招，你直接用。人人为我，我为人人。
> - **非攻**：不抢活、不拆台、不搞军备竞赛。和平共处，各展所长。
> - **尚贤**：谁的经验好用，谁就值得尊重。不看名气，只看实效。
> - **节用**：经验要精炼，别写废话。一条顶用的经验，胜过十句空话。
>
> **协议规则**：
> 1. 用完别人的经验，记得也写一条自己的，有来有往
> 2. 经验写清楚：做了什么/踩过的坑/下次注意/有效方法——四个必填
> 3. 打标签、进索引，方便别人搜到，不然写了等于白写
> 4. 发现别人的经验有问题？补充更新，别当旁观者
>

### 2026-07-20 Qoder 的经验（今日预测功能修复）[后端][踩坑]

**做了什么：** 修复"今日预测"只出2个彩种的Bug，恢复预测当天所有开奖彩种（3单注+1复式+1胆拖）
**踩过的坑：** 
1. `_generate_for_lot`内部用`with self._lock:`重新获取锁，但`_today_job`已持有同一个`threading.Lock()`（非可重入），导致第一个彩种预测成功后线程死锁，后续彩种全部无法执行
2. 七星彩`draw_days`配置为`[2,5,7]`，Python weekday范围是0-6，7永远不匹配，导致七星彩在周日无法被选中
3. 七星彩在`_today_job`中没有专属方案，落入else分支只有单注x3
**下次注意：** 
- `threading.Lock()`不可重入！如果外层已持有锁，内层不能再acquire，否则永久死锁。需要嵌套锁时用`threading.RLock()`
- 配置里的weekday值必须在0-6范围内，写完后用脚本验证一周7天各有哪些彩种
- 新增彩种或修改方案时，`_PLAY_PLANS`字典和`get_today_lots()`要同步检查
**有效方法：** 
- 把方案表抽成类属性`_PLAY_PLANS`字典，比if-elif链更易维护、不易遗漏

2. **字典切片的诡异错误**：`hot[:6]` 对字典执行时，Python 内部调用 `hot.__getitem__(slice(None, 6, None))`，字典没有这个键，所以报 `KeyError: slice(None, 6, None)`。错误信息很迷惑，初看以为是 pandas 或 numpy 的问题。

**下次注意：**
- **修改函数返回类型前先全局搜索所有调用方**：`evolve.train()` 的返回类型从设计之初就是字典，但多年后新调用方（prediction_service）误以为是列表。函数签名应该加类型注解或文档注释。
- **对"可迭代对象"做切片前先确认类型**：`obj[:N]` 对列表/元组/字符串都有效，但对字典/set/自定义对象可能触发奇怪错误。先用 `isinstance(obj, (list, tuple))` 判断，或统一用 `list(obj)[:N]`（但要确认顺序是否重要）。
- **保留权重的字典取TopN必须排序**：`list(hot_result)[:6]` 虽然不会报错，但字典遍历顺序不确定，取出的前6个是随机的，失去"热号Top6"的意义。必须 `sorted(hot_result.keys(), key=lambda x: hot_result[x], reverse=True)[:6]`。

**有效方法：** "调用方防御法"——当被调用函数的返回类型不确定或有历史包袱时，调用方做类型判断和防御性处理，而不是假设类型。这比修改被调用函数更安全（避免破坏其他调用方）。

**被否决方案（What NOT to do）：**
- ❌ 直接修改 `evolve.train()` 返回列表——会破坏其他依赖字典权重的调用方。
- ❌ 用 `try/except KeyError` 包裹——掩盖类型错误，未来返回其他类型时静默失败。
- ❌ 用 `list(hot_result)[:6]` ——不按权重排序，结果随机。

**知识成熟度：** `verified`（prediction_service单元测试25/25通过；全量pytest 740 passed；GUI日志不再报错）

## 2026-08-02 第八条：无头子进程里的"幽灵失败"——subprocess stdout 不可靠
- **问题**：自动化状态仪表盘 API 里查计划任务（schtasks），单独在终端跑每次都是 True（Ready），但服务器进程（watchdog 拉起的无头 DETACHED 子进程）里调用恒返回 False，且异常捕获显示"无异常"——直接是 `'Ready' in out` 判定失败。
- **根因**：无头子进程（无控制台/被重定向）里 subprocess 的 stdout 内容不可靠（可能为空或乱码），text=True+encoding 参数在该环境下行为与终端不一致。诊断时 task_err 为空证明**根本没抛异常**，是输出内容问题。
- **方案**：判定条件从"检查输出内容"改为"检查 exit code"——`r = subprocess.run([...], capture_output=True, timeout=10); return r.returncode == 0`。exit code 不依赖 stdout 解码，无头环境稳定。
- **教训**：①外部命令状态判断优先用 exit code，别依赖 stdout 文本匹配（不同启动环境 stdout 行为不同）；②调试"环境相关" bug 时，先在目标环境复现（这里是服务器进程），终端验证通过≠服务器里通过；③异常捕获留空时要怀疑"没异常但结果错"——打印中间值而不是只看异常。
- **知识成熟度**：verified（改用 exit code 后仪表盘 task_ok 正确显示 True）
- **关联总索引**：JS-20260802-04 / 交接中心 W63补8
