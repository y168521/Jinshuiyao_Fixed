## 0. 一句话结论（给用户的版）

彩票生成的「置信度」**不能**是「中奖概率」——`JS-20260723-37` 已证明诚实基准近 0（福彩3D 0.00% / 排列三 1.11%），给个百分比会把用户骗去当真。正确做法是设计一个**信号质量指数 SQI**（Signal Quality Index）：只反映「模型这期信号清不清晰、数据干不干净」，配一句**强诚实声明**防误读。后端由我落地，前端档位展示交给 Qoder/TRAE（延续分工）。

## 2. 三维框架分析

### 2.1 方案探索（4 候选，已对比优劣）

| 方案 | 思路 | 优劣 | 结论 |
|------|------|------|------|
| **A 历史命中率代理**（复用 R1） | 统计每期「预测 vs 开奖」命中率 | ✗ 被 `JS-20260723-37` 否决：诚实基准近 0，恒≈0 无信息量；且「命中」口径争议大（直选/组选/单注/复式） | **否** |
| **B 信号清晰度代理** | 用 hurst 趋势明确度 + 热号权重集中度 + 杀号确定性 + 多引擎共识合成 | ✓ 诚实表达「系统当下状态」，有信息量，不冒充概率 | **主用** |
| **C 数据质量代理** | 新鲜度 + 历史长度 + 缺失率 | △ 偏外围，单独信息量低，宜作**门槛**而非主信号 | **作门槛** |
| **D 不确定性量化**（贝叶斯/熵） | 概率模型输出预测区间 | ✗ 过度工程，违反架构铁律；需强加概率假设，反而更易造假 | **否** |

### 2.2 策略整合（取长补短）

主用 **B**，叠加 **C** 作门槛（数据陈旧/不足直接降级），形成：

```
SQI = 0.30·hurst_clarity + 0.25·hot_concentration + 0.20·kill_certainty + 0.25·engine_consensus
若 data_quality < 60：SQI = min(SQI, 40) 且 level 至多 medium（数据差强制降档）
```

### 2.3 参考调研（业界最佳实践佐证，非编造）

- **彩票软件行业**：冷热号热度指数、遗漏值、走势形态评分是通用做法，**从不宣称中奖概率** —— SQI 契合该惯例。
- **量化金融「模型置信度」**：= 预测区间宽度 / ensemble 离散度（**非概率**）—— 借鉴「多引擎意见分歧=共识度」思路（`engine_consensus`）。
- **统计社区共识**：对近随机过程不应输出伪概率（呼应 JS-37 教训）。

### 2.4 正反推导（方案选定后交叉验证）

- **正向思维**（从目标推导系统应具备的能力）：目标=帮用户判断参考价值 → 需输出「可读档位 + 信号明细 + 诚实说明」→ 方案 B 覆盖。
- **逆向思维**（从故障模式反推必堵漏洞）：
  1. 用户误读成「中奖概率」 → **语义隔离**（命名 + 前端强提示 + 诚实声明）
  2. 信号全开但彩票本随机 → 即使 SQI 高也不可信为概率 → **配套诚实声明**
  3. 旧客户端不读 confidence → **向后兼容**（新增字段，旧字段不变）
  4. 信号计算异常（hurst/hot 算出错） → **fail-safe**（confidence 必须返回不崩，绝不 None 导致前端崩）
- **交叉比对（正向 ∩ 逆向 = 必做项）**：信号质量档位 + 语义隔离 + 诚实声明 + 向后兼容 + fail-safe。

## 3. 推荐方案（SQI 设计，可落地）

### 3.1 字段结构（`generate()` 返回新增 `confidence`）

```json
"confidence": {
  "score": 0-100,
  "level": "strong | medium | weak | unknown",
  "signals": {
    "hurst_clarity": 0-100,
    "hot_concentration": 0-100,
    "kill_certainty": 0-100,
    "engine_consensus": 0-100,
    "data_quality": 0-100
  },
  "note": "信号质量指数(SQI)：反映模型当前信号清晰度与数据质量，非中奖概率。彩票本质近随机。"
}
```

### 3.2 各信号计算（具体、可编码）

| 信号 | 计算 | 备注 |
|------|------|------|
| `hurst_clarity` | `clamp(|hurst-0.5|/0.5, 0, 1)·100` | `hurst` 需 `len(arr)>=50` 才有值，否则记 **50（中性）** |
| `hot_concentration` | `top6 权重和 / 总权重 · 100` | `hot` 为 dict 时按权重；list 时按出现频次归一 |
| `kill_certainty` | 杀号数合理度（5–30 个为宜，过多/过少降分）+（智能杀手历史准确率 *若有* 否则中性 50） | 复用 `smart_killer` 若可用 |
| `engine_consensus` | `vote_mode` 多方案一致度；无 vote 则按**启用引擎数**归一（越多引擎共识=越高） | 复用 `self.engine_states` |
| `data_quality` | 新鲜度（OK=100 / stale 降档）× 历史期数（≥100=100，50–100 线性，<50 降） | 复用 `Data.is_fresh()` / `freshness_minutes()`（JS-37 已加） |

### 3.3 合成与档位

```
SQI = round(0.30·hurst_clarity + 0.25·hot_concentration + 0.20·kill_certainty + 0.25·engine_consensus)
档位：score ≥ 70 → strong；40–69 → medium；< 40 → weak
若 data_quality < 60：SQI = min(SQI, 40)，level 至多 medium
```

### 3.4 fail-safe（头号坑）

新增 `_compute_signal_quality(...)` **整体 try/except**：
- 任一子信号异常 → 该信号记 **50（中性）** 继续，不中断主流程；
- 整体异常 → 返回 `{"score": null, "level": "unknown", "note": "信号计算暂不可用"}`，**绝不抛异常**影响 `generate()` 主返回（L344-352 仍正常返回 tickets）。

## 7. 遗留 / 风险（诚实）

- ⚠️ **语义隔离是头号风险**：命名 / 前端必须明确「非概率」，否则 `JS-20260723-37` 教训重演（用户误以为高 confidence = 高命中）。
- ⚠️ 与 R1 的 `confidence` **语义不同**（R1 = 历史命中率代理；本 = 信号质量），前端**不可混用**同一解释逻辑。
- ⚠️ 知识库 `cards_used` 波动可能让 confidence 抖动 → 建议 kb 仅作微调因子（非主权重），保证稳定。
- S2 历史核对模块若做，命中率恒≈0，仅作透明展示，绝不作为置信度信号。
