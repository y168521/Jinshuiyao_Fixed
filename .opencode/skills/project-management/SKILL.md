# 项目管理技能

## 适用场景
- 个人/小团队软件项目管理
- 版本规划与迭代管理
- 需求拆解与任务排期
- 风险识别与应对

## 项目启动阶段

### 需求拆解 WBS
把大项目拆成可执行的小任务：
- 每个任务不超过 2-3 天工作量
- 每个任务有明确的交付物
- 任务之间的依赖关系清晰

### 里程碑设定
每个大阶段设一个里程碑：
- M1：数据层完成
- M2：分析层完成
- M3：展示层完成
- M4：打包部署完成
- M5：测试完成，正式发布

## 迭代规划

### 版本号规范
```
主版本号.次版本号.修订号
  │        │       └── 修复bug、小优化
  │        └────────── 新增功能，向下兼容
  └─────────────────── 大版本升级，可能不兼容
```

### 迭代周期
- 小迭代：1-2周，修复bug+小功能
- 中迭代：2-4周，一个完整模块
- 大版本：1-3个月，架构级升级

## 任务管理

### 任务优先级
- **P0 紧急**：阻塞开发、线上bug，必须立刻做
- **P1 高**：本版本核心功能，必须完成
- **P2 中**：重要但不紧急，有时间就做
- **P3 低**：优化、想法，排期有空再做

### 任务状态流转
```
待办 → 进行中 → 待测试 → 已完成
       ↓
     阻塞
```

## 风险管理

### 常见风险
| 风险 | 概率 | 影响 | 应对方案 |
|------|------|------|----------|
| 第三方API挂了 | 中 | 高 | 准备备用数据源，加缓存 |
| 某个模块比预想复杂 | 高 | 中 | 预留缓冲时间，先做最小可用版 |
| 环境问题打包失败 | 中 | 中 | 提前测试打包，不等到最后 |
| 需求变更加功能 | 高 | 高 | 控制范围，新需求放下个版本 |

### 风险应对策略
1. 规避：换方案，从根源消除风险
2. 减轻：降低概率或影响
3. 转移：交给别人处理
4. 接受：影响不大，发生了再说

## 进度控制

### 每周检查点
每周花10分钟复盘：
1. 本周完成了什么
2. 进度比计划快还是慢
3. 遇到了什么问题
4. 下周计划做什么

### 延期处理
发现要延期了：
1. 立刻评估影响
2. 砍范围：非核心功能放下个版本
3. 调优先级：只做 P0+P1
4. 调时间：重新评估工期

## 质量管理

### 代码质量检查点
- [ ] 核心模块有注释
- [ ] 异常情况有处理
- [ ] 边界情况测试过
- [ ] 没有硬编码的魔法数字
- [ ] 重复代码抽成函数

### 测试清单
- [ ] 正常流程跑通
- [ ] 异常输入不崩溃
- [ ] 空数据处理正确
- [ ] 大数据量不卡死
- [ ] 打包后能正常运行

## 发布流程

### 版本发布标准步骤
1. 功能冻结，不再加新需求
2. 全面测试，修复bug
3. 更新版本号和更新日志
4. 打 Git tag
5. 打包构建
6. 小范围验证
7. 正式发布

### 更新日志规范
```
## [24.0.0] - 2024-06-01

### 新增
- 新增泊松预测模型

### 优化
- 数据导入速度提升3倍

### 修复
- 修复跨度计算错误的问题
```

## 个人开发者最佳实践

### 1. 先跑通，再优化
- 第一版先把核心流程走通
- 能用了再慢慢优化

### 2. 控制范围，抵制需求膨胀
- 新需求记下来，放下个版本
- 不然永远发布不了

### 3. 小步快跑，频繁提交
- 每个小功能完成就 commit
- 出问题容易回退

### 4. 文档跟着代码走
- 接口改了，文档同步改
- 别等最后补文档，肯定忘

### 5. 留缓冲时间
- 估时 × 1.5 比较靠谱
- 总会有预料之外的问题
