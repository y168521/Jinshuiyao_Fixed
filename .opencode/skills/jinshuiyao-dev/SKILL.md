# 金水谣开发协作与代码维护规范

> 来源：2026-07-21~07-24 历史经验蒸馏（WorkBuddy/opencode 会话），2026-08-02 整理入库。

## 代码审查与合并

- **合并前先判断"真冗余"还是"分域实现"**：改名检查标"重复"的模块，多数是分域实现（通用 vs 足球域等），**不能盲并**；只有真正的壳+实现（如 engines/killer.py 壳 + killer_fixed.py 实现）才安全合并。
- **安全合并四步**：内联 → 转引用 → 删壳 → 跑单测验证（如 `from engines.killer import Killer` 成功 + test_engines 25 passed）。
- **代码审查**：审查要覆盖"遗漏修补"——改完一处要全链路交叉验证相关调用点（同 2026-07-29 opencode 经验）。

## 大文件编辑

- 大 HTML/MD 用 Edit 工具常报 "File has not been read yet"（即便分段 Read）。
- **更稳的方案**：用 Python 补丁脚本做精确替换（`str.replace` + `count==1` 断言），或整文件重写。

## 多模型接力防乱

- 根治"启动快照污染"：多模型（WorkBuddy/opencode/DeepSeek 等）接力时，防乱机制 = **Lint 自动化 + 备份隔离守卫**（2026-07-21 落地）。
- 启动器"打不开"根治套路（2026-07-22）：**日志落盘 + 独立窗口 + pip 稳健安装**，三步排查法。

## 测试与覆盖率

- 覆盖率分析（2026-07-21）：补充测试让代码变更验证更可靠；改完代码必须跑相关测试（test_engines.py 等）确认无回归。
- 项目测试基线：`venv python -m pytest tests/ -q`（约 814 项）。

## 自检清单

1. 模块"重复"检查时先确认是否分域实现？
2. 大文件改动是否改用 Python 补丁脚本？
3. 改完是否跑了相关测试？
4. 多模型接力是否触发防乱机制（Lint+备份）？
