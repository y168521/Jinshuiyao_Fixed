金水谣 · 启动 AI 知识库搭建手册

面向多 AI 接力协作的个人/项目知识库体系。讲清：知识库是什么、七层闭环怎么转、Obsidian 怎么接、门禁怎么卡、以及——删东西怎么才不翻车。
本手册由 AI 依据项目现有体系（启动提示词.txt / 提示词库.html / obsidian-vault / closeout_gate.py / safe_cleanup.py）重建（JS-20260727-14）。

为什么需要这本手册？ 一次常规清理中，某个会话把"清理金水谣数据/"理解成整目录 rm，没区分独有文档 / 运行时杂物 / 活跃文档，导致一份从未提交 git 的独有手册被循环删除、永久丢失。根因＝删除环节"没细致划分 + 无闸门 + 无兜底"。本手册第 6 节给出经实测的安全删除框架，直接从机制上根除该漏洞。

1. 知识库是什么（金水谣的三类知识）

金水谣的知识不在某个神秘数据库里，而是三层纯文本 Markdown，机器和人都能读：

层文件作用谁来写
① 协作层AI协作交接中心.md
工作留痕总索引.md		进度/待办/分工；所有改动按 JS-编号 登记AI 收工必写
② 决策层Jinshuiyao_Fixed/金水谣数据/log/ai_decisions.mdAI 决策卡（8 字段：属主/做了什么/为什么根因/验证/坑/有效方法/关联文件/关联总索引）AI 每任务必写
③ 运营层.workbuddy/memory/MEMORY.md
.workbuddy/memory/YYYY-MM-DD.md		长期铁律 + 每日日志（AI 状态，人手别改）AI 自动维护

另有 经验收集箱.md（踩坑/有效方法）、graph_triples.json（2156 条语义三元组，给 AI 离线检索用）。这些才是"知识库"的真身——不是 Obsidian，Obsidian 只是它的阅读视图（见第 4 节）。

2. 七层知识闭环（知识要复利，不要漏斗）

核心原则：一件事只在一处写（单一真源），写一次自动传播到所有下游。断任一环＝复利变漏斗。

① 干活→ ② 写 memory→ ③ 登记总索引→ ④ 写 ai_decisions 决策卡→ ⑤ (自动)知识卡片+三元组→ ⑥ Skill/自动化→ ⑦ 启动提示词→ 回到①下一轮

每个箭头都有门禁/自动化兜底。例如 ③→④ 由 closeout_gate.py 的 [B] 项反向核对（见第 5 节）；④→⑦ 由每周"启动提示词同步"Skill 保证。

致命禁忌：禁止对"金水谣数据/"这类目录下宽指令整目录删除。任何清理必须先分类、先 salvage、低风险才删（见第 6 节）。曾因此丢失独有文档。

5. 收工门禁：closeout_gate（防漏，不是靠记性）

说"完成"之前必须跑（每日 23:30 自动化已接）：

py -3.14 Jinshuiyao_Fixed/scripts/closeout_gate.py   # 全绿=CLOSEOUT-OK，退出码0
项核对内容抓什么漏
[A]git 待提交 / gitignore 隐患漏提交的源码、泄漏的运行时文件
[B]今日总索引每个 JS 编号是否都进 ai_decisions.md干了没写知识库
[C]今日决策卡 8 字段完整卡写残缺
[D]启动提示词 mtime 今日同步铁律改了没同步入口
[E]今日每个 commit 的 JS 编号是否登记总索引有 commit 没登记（跨会话断链，曾抓中 JS-07/08/09、JS-12）
[E] 项是反向核对：从 git log --since=midnight 抓 JS 编号，反向比总索引标题。任何会话（含跨会话）提交的编号若没登记，会被点名。这是"纸面打通≠真打通"的硬保险。

6. 安全删除框架（JS-20260727-14 · 事故后优化）

取代"宽指令 rm 整目录"。四道保险：①只读扫描先行 ②七类精细划分 ③SALVAGE 兜底 ④三级闸门。

6.1 七类精细划分（每文件归一类，区分价值）

类别判定风险闸门
运行时杂物*.log / _kb_backup_*.json / *.bak.* / watchdog* / video_cache低自动（需 --apply）
冲突残留*冲突* / *.orig / *.rej / *.mine低自动（需 --apply）
死文件git 跟踪、全仓零引用、无权威副本中需 --apply
冗余副本仓库内有同名权威文件（另一处）中需 --apply
独有文档人读知识(.md/.html)，零引用、无副本高需 --confirm-unique
活跃引用被代码/索引引用高需 --confirm-unique
未提交新文件git 未跟踪且未忽略，价值未知高需 --confirm-unique

6.2 用法

# 1) 只读分类报告（默认，零副作用）——先看清再决定
py -3.14 Jinshuiyao_Fixed/scripts/safe_cleanup.py <路径>

# 2) 执行：低风险+中风险删，高风险的独有/活跃/未提交会拒绝(🛡)
py -3.14 Jinshuiyao_Fixed/scripts/safe_cleanup.py <路径> --apply

# 3) 确要认真删高风险项：显式加 --confirm-unique（仍需先 salvage）
py -3.14 Jinshuiyao_Fixed/scripts/safe_cleanup.py <路径> --apply --confirm-unique

6.3 三重硬约束（任何模式都生效）

  • SALVAGE 兜底：删前把拟删文件全拷到仓库外 ../_cleanup_salvage/<时间戳>/（循环删/误删都能找回，已实测持久化）。
  • 不递归 rm：只逐文件删"已分类且过闸门"的项，结构上杜绝整目录误删。
  • 仓库外拒绝：目标在仓库外（如 C:/Windows）或位于 .git/ 内 → 直接拒绝（退出码 3）。
铁律：删 tracked 文件后必须单独 git commit 入库，切勿把独有文档的删除和清理混在同一批提交——这正是事故扩大的原因。

7. 防 AI 惰性 · 五道防线（摘要）

  1. 检索前置：动手前读全上下文（交接中心+总索引+经验箱+源码），禁凭印象下结论。
  2. 引用门禁：任何结论附证据（文件:行号/命令输出/数据），无引用＝未做。
  3. 原子化：一次最多领 2-3 个任务，做完验完再领下一批。
  4. 濯石淘洗：硅基流动免费模型(THUDM/GLM-4-9B-0414)只在项目代码内部干脏活省费，不替代 DeepSeek 核心质量。
  5. 主动抽考 + 不闭塞：收工随机抽考当日文档细节；结论受外部影响时先联网核验，禁闭门造车。
