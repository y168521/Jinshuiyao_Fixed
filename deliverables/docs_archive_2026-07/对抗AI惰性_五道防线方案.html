对抗 AI 惰性 · 五道防线

金水谣项目 · 针对「长文本被粗略略过、缺乏认真思考」的深层机制设计 · 2026-07-27

!问题本质

AI 在长上下文里并非「逐字精读」，而是受 注意力近因偏差（recency bias） 与 长度导致的粗略扫读 影响：当一段长文档（日志、历史对话、规范库）整体塞进上下文时，模型容易「看起来读过了」就下结论，跳过中间关键段落，且缺少强制验证机制时不会自曝「没读全」。

这与人的惰性同源——信息过载时大脑也启动「略读+脑补」捷径。所以对抗方法不是「要求更认真」，而是从流程上让惰性无法发生：把长文本拆小、强制引用证据、用便宜模型先做脏活、定期抽考验证。

1检索前置（Retrieval-First）流程红线

原理：禁止「整本文档塞进上下文再读」。先由工具抽取关键片段置顶，再让模型处理。

  • 落地：处理 >2000 字文档前，先用 Grep/grep 定位相关段落，只把命中片段 + 行号交给模型；Obsidian vault 用 [[wikilink]] 导航而非通读全库。
  • 铁律：凡引用长文档结论，必须「先检索后引用」，禁止「我大致看了一下」式断言。
已生效：Obsidian 双链（JS-20260727-06）让知识库可导航而非通读；前端巡检/健康日报等 Skill 均走「脚本抽取→模型判断」而非模型通读。

2引用门禁（Citation Gate）强门禁

原理：每段结论必须标注可复核证据，无引用即「未证实」。

  • 落地：凡输出「已修复 / 已验证 / 已对齐」类断言，必须附 📌 依据：<文件#行号> 或命令输出片段。
  • 门禁：在「收工自检」「知识体检 Lint」中加「结论—证据」配对检查；无证据的断言标记为【未证实】回退重做。
  • 铁律：跨文件/跨会话的结论，必须在总索引或交接中心登记可溯源编号（JS-/TS-）。

3原子化（Atomic Processing）流程红线

原理：一次性吞下大文档再略过，是惰性的温床。拆成 ≤1 个逻辑单元，逐个处理并即时反馈。

  • 落地：文档审查按章节原子化；多文件改动用 TaskCreate 拆任务，逐个标记完成；单轮只处理一个逻辑单元。
  • 铁律：跨单元的结论需在单元边界做「已读确认」——未确认不得跨单元引用。
已生效：本会话 git 收尾即拆成「补 gitignore / 取消跟踪 / 提交源码」三个原子任务逐一完成，避免一次性漏改。

4濯石淘洗（Zhuoshi Pre-filter）已落地

原理：便宜模型（濯石 / zhuoshi）承担「读全 + 结构化」脏活，贵模型（DeepSeek）只做高价值决策。濯石读全成本低，惰性代价小；贵模型只看结构化结果，不被长文本淹没。

  • 落地：长文档分析流程 = 濯石抽取摘要 / 矛盾清单 / 待核实项 → 人工或 DeepSeek 基于结构化结果复核。
  • 已落地：今日已将全部 10 个维护型自动化（看门狗 / 诚实回测 / 记忆蒸馏 / 健康巡检 / 基金日报 / 提示词同步 / 收工自检 / 数据源健康 / GraphRAG 调和 / 知识体检 Lint）钉死 modelId=zhuoshi + modelIsThinking=false。让便宜模型承担运维脏活，贵模型留给真正的推理与创作。

5主动抽考（Active Quiz）建议新建 Skill

原理：定期随机抽查 AI 是否真读全，答不出 = 读不全，触发重读。把「自检」变成不可跳过的关卡。

  • 落地（建议）：新建自动化 Skill jinshuiyao-ai-diligence-check——每次收工或 AI 接力交接时，从当日处理的文档随机抽 1–2 个细节提问（如「第 X 章第 Y 节说了什么」「文档里哪个结论与 Z 矛盾」），答不出则判定读不全并强制重读该段。
  • 铁律：多 AI 接力时，接手方必须先用 1 个抽考问题验证前一手真读过，否则不接手。
  • 复用：可嵌入现有「知识体检 Lint」做交叉验证，不另起炉灶。
