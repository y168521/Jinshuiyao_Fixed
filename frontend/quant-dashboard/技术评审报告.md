## 一、四象限布局比例及小屏自适应

### 问题清单
1. 🟡 **【P2】超宽屏下象限被横向拉伸**：固定 `2×2` 在 ≥2560px 屏幕上每格过宽，分时图信息密度反而下降。
2. 🟢 **【P3】移动端 <520px 时终端字号偏小**：`--font-mono` 在窄屏未额外缩放。
3. 🟢 **【P3】面板头部在堆叠态未显示当前标的**：小屏单列时左上标题仍写死"高频 TICK 分时图"，未携带指数名。

### 优化方案（可落地）
- 给 `.grid` 增加 `max-width` 与 `margin:auto`，超宽屏限制单格最大宽度（如 `minmax(0, 760px)`），保持信息密度。
- 在 `@media (max-width:520px)` 中把 `.terminal{font-size:11px}`、`.metric .v{font-size:18px}` 微调，并给面板头部注入 `#symName`（已在 topbar 有，可下拉同步到面板 header）。
- 用 CSS 变量统一断点（如 `--bp:900px`），避免魔法数字散落。

```css
.grid{ display:grid; grid-template-columns:repeat(2,minmax(0,1fr));
        gap:14px; max-width:1640px; margin:0 auto; }
@media (max-width:900px){ .grid{ grid-template-columns:1fr; } }
```

## 二、外部 API 调用：超时 / 重试与 JSON 解析容错

### 当前实现（已达标）
- `EventEngine.callLLM`：`AbortController` 超时（`timeoutMs` 默认 8000）→ 失败 `600·2ⁿ` 指数退避重试（默认 3 次）→ 全程 `try/catch` 降级 mock。
- `parseJSON`：剥离 ```json 围栏 → 截取首 `{` 尾 `}` → `JSON.parse` → 失败正则兜底抽 `summary` → `normalize` 对 `sectors` 逐字段 `clamp`+默认。
- 真实数据层 `DataSource.load`：`/api/stock` 失败回退 `data/real_stock.json` 静态快照；非法标的被服务端 400 拦截。

### 问题清单
1. 🟡 **【P2】重试不区分错误类型**：网络超时（应重试）与 4xx（不应重试）一视同仁，4xx 也做退避浪费 ~4.2s。
2. 🟡 **【P2】缺请求体大小 / 流式保护**：若 LLM 返回超长文本，单次 `await resp.json()` 可能占内存；无 `response.clone()` 调试留存。
3. 🟢 **【P3】mock 与真实路径的错误日志未带 requestId**：多事件并发时难以追踪。

### 优化方案（可落地）
- 在 `catch` 中读取 `e.name==='AbortError'` 与 `resp.status`：仅对超时/5xx/网络错误重试，4xx 直接降级。
- 增加响应大小上限：`const buf=await resp.arrayBuffer(); if(buf.byteLength>1<<20) throw new Error('resp too large');`
- 给每次 `run()` 生成 `traceId`（时间戳+随机），贯穿 Terminal 日志，便于排查。

## 三、高频数据流渲染性能（ECharts 更新 / 日志滚动）

### 当前实现（已达标）
- 分时图：`chart.setOption({series:[...]},{lazyUpdate:true})`，且由 `requestAnimationFrame` 节流，每帧最多重绘一次；数据窗口 `state.ticks` 限长 `window*2`。
- 终端：日志先入 `pending` 队列，`rAF` 批量 `DocumentFragment` 写入，行数 `cap=200` 截断防 DOM 膨胀。
- 信号引擎：监听 `tick` 事件 `recompute()`，纯内存计算无重排。

### 问题清单
1. 🟡 **【P2】ECharts 每次重绘仍重建 series 数据引用**：虽 `lazyUpdate`，但未用 `appendData`（更适合流式追加），高频下 GC 压力略高。
2. 🟡 **【P2】`markDirty` 每 tick 全量 `map` 生成新数组**：`priceData`/`chgData` 每次重建两个 N 长度数组（N≤240），tick 220ms 下尚可，但可改为增量 push。
3. 🟢 **【P3】`resize` 仅防抖未节流**：连续拖拽窗口时仍多次 `chart.resize()`。

### 优化方案（可落地）
- 改用 `chart.appendData({seriesIndex:0, data:[point]})` 增量追加，仅在首次 `setOption` 建结构；配合 `dataZoom` 自动滚窗。
- `markDirty` 改为：维护定长环形缓冲，仅 push 新点、shift 旧点，避免每帧 `slice+map` 整段重建。
- `resize` 用 `util.rafThrottle` 包裹，与渲染同帧。

## 四、信号指标计算逻辑的可解释性与动态调整

### 当前实现（良好）
- 七指标均给出可读公式（卡片底部 `formula`）：
  - VOL = 量比×40 + 分时活跃度（量比=最新量/20日均量，真实）
  - SCORE = Σ wᵢ·指标（动量/波动/量能·日频），权重滑块即时生效
  - 胜率 = 近 20 日上涨占比（真实日线）
  - 风险 = 日收益年化 σ×√252
  - 仓位 = 凯利 `f=(p(b+1)-1)/b`
  - EV = `p·b-(1-p)`
- **真实化改造**：SCORE/胜率/风险/赔率/仓位/EV 现已全部基于 `金水谣数据/stock/cache` 真实日线计算，不再来自随机游走。

### 问题清单
1. 🟡 **【P2】缺单位与置信区间**：如"胜率 55%"未标注样本量（近 20 日），读者难判显著性。
2. 🟡 **【P2】动量窗口写死 20 日**：未与 UI 周期选择联动（短/中/长）。
3. 🟢 **【P3】`liveVol` 叠加使 VOL 概念略混**：真实量比与分时活跃度混算，公式虽写清但易误解。

### 优化方案（可落地）
- 胜率旁显示 `(n=20)`；风险显示年化 `%` 与对应历史区间。
- 暴露 `window` 配置（5/20/60）到 UI，SCORE 动量项改用所选周期 MA。
- 将 VOL 拆成两个独立卡（真实量比 / 分时量能），各给公式，避免语义叠加。

## 五、终端日志视觉冲击力

### 当前实现（良好）
- 方向配色：`▲` 红（涨）/ `▼` 绿（跌，A股习惯）/ `■` 灰；风险分级 `[HIGH]`红 `[MID]`琥珀 `[LOW]`青，配 `text-shadow` 发光。
- 日志淡入动效（`.log-line` 入场过渡），自动滚底。
- 扫描线全局覆盖（`.scanlines` body 类）。

### 问题清单
1. 🟡 **【P2】无"高亮告警"脉冲**：`HIGH` 风险行未做呼吸/闪烁强调，关键时刻易被淹没。
2. 🟢 **【P3】同色行密集时层次弱**：连续同方向日志缺乏分隔节奏。
3. 🟢 **【P3】缺可选音效/勿扰开关**：纯视觉，长时间监控疲劳。

### 优化方案（可落地）
- `risk-HIGH` 行加 `@keyframes alarmPulse` 红边呼吸（1.2s），并在该行左侧加 `▮` 警示条。
- 每隔 N 行插入极淡分隔线（`border-top` 2% 白）建立视觉节奏。
- 提供右上角"🔔 告警音"开关（WebAudio 短 beep，默认关），与扫描线同属视觉/听觉增强。

## 六、代码解耦、状态管理、渲染优化与可维护性

### 当前实现（达标）
- **单一状态源** `state` + **事件总线** `bus`（`on/emit`），四引擎（`Tick/Chart/Signal/Event/Terminal`）互不直调，仅通过 `bus` + `state` 通信。
- **分层**：`index.html`（结构）/ `styles.css`（视觉）/ `app.js`（逻辑）三文件解耦；`DataSource` 与 `UI` 作为横切模块。
- **工具收敛**：`util`（clamp/sma/std/rafThrottle/debounce）复用，避免重复实现。
- **后端零依赖**：`quant_server.py` 仅用标准库，同源解决 CORS，暴露 `stock`/`knowledge` 两类真实数据。

### 问题清单
1. 🟡 **【P2】`state` 字段分散**：`predictionLog` 现已弃用（改真实胜率），残留空数组，应清理。
2. 🟡 **【P2】`EventEngine.run` 串行依赖**：先 `getContext` 再 `callLLM`，上下文失败会拖慢推演；可并行 `Promise.all`。
3. 🟢 **【P3】无类型/单元测试**：纯前端，缺对 `parseJSON`/`normalize` 的自动化校验（历史 JSON 异常样本）。

### 优化方案（可落地）
- 删除 `state.predictionLog` 及引用，信号胜率统一走真实日线。
- `run()` 改为 `const [ctx]=await Promise.all([this.getContext(prompt)])`（为后续并行预置），上下文失败不阻断主推演。
- 增加 `tests/` 前端单测（Vitest/Jest）覆盖 `parseJSON` 的围栏/截断/字段缺失三种异常，CI 跑通。

## 九、本轮续做增强（2026-07-18 续）

在首版评审交付后，按"演示级→可用级"方向落地三项增强，并修复一个服务端隐性 bug。

### 9.1 信号引擎历史回测真实化（可解释性核心）
- **问题**：原"胜率/EV"由合成滚动预测得出，不可信、不可复核。
- **方案**：新增 `computeBacktest(closes, 20)`，用真实日线对"20日动量信号"做历史方向判定：
  - `win` = 下一交易日方向命中率（真实"胜率"来源）；
  - `maxdd` = 多头策略权益曲线最大回撤；
  - `sample` = 有效样本天数。
- **验证（上证指数近120日真实数据）**：样本 99 天、历史方向胜率 **49.49%**、最大回撤 7.89%。
  结果诚实地接近硬币翻转——说明单纯日频动量对宽基指数预测力有限，比伪造高胜率更有价值。
- 右上信号面板新增 `回测(20日动量策略) · 样本N日 · 历史胜率X% · 最大回撤X%` 底部条。

### 9.2 事件推演结论回写知识库（学习闭环）
- **方案**：`quant_server.py` 新增 `POST /api/knowledge`（幂等 upsert，按 title 匹配，存在则 `use_count+1` 并更新 content）。
  `EventEngine.writeBack()` 在每次推演后把结构化结论写成 `event_deduction` 钩子的卡片回写金水谣 MiroFish。
- **效果**：下次 `/api/knowledge` 检索会把"金水谣自己的历史推演记忆"注入 LLM 提示词，形成越用越聪明的闭环。
- **验证**：POST 首写 total 90→91；同标题复写 `use_count` 自增、content 更新（幂等通过）。

### 9.3 分时图真实感增强
- `TickEngine` 锚定真实当日 `open/high/low/close`：价格被约束在 `min(昨收,当日最低)`~`max(最新收盘,当日最高)` 包络内，分时线落在真实当日区间。
- 成交量采用 **U 型日内剖面**（开盘/收盘放量、午间缩量）+ 对价格跳变敏感，模拟更真实的高频量能节律。

### 9.4 修复：服务端隐性 bug
- `quant_server.py` 的 `build_stock_payload` 调用了从未定义的 `find_cache()`（原文件仅有一段不可达的遗留循环，非函数定义），导致 `/api/stock/<sym>` 一直 500/连接失败。
  补回正确的 `find_cache()`（遍历 `CACHE_DIRS` 定位真实日线缓存）。修复后 `/api/stock/sh000001` 返回真实收盘 3913.794（live=True，日线120条）。
